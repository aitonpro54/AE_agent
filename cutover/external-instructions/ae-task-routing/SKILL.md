# Маршрутизация AE-задач

## Обязательный выбор блока

Перед каждым самостоятельным блоком и после сложного блокера выбирай исполнителя по scope: Luna для простых сгруппированных фактов, результатов и правок по образцу; Sol/high для scoped реализации, отладки и содержательной технической валидации; Flash configured High только для ограниченных правок с ясной приёмкой в подтверждённых категориях.
Готовый валидатор — льгота одному короткому вызову, не длительной серии routine checks.
Исключение требует конкретной краткой записи причины; выбор модели чата сам по себе override не является.
Для bounded поручений native Codex ставь `fork_turns: none` и явно передавай цель, нужный контекст, ownership и приёмку. Flash получает task packet, без поля fork.
Один live-контроллер и лимит helpers сохраняются.
Подробная политика только для legacy `AE_agent`: C:/Users/Ant/Documents/Codex/AE_agent/docs/routine-dispatch-policy.md.

## AE Agent route: Core and legacy

Таблица ниже — рекомендуемая dispatch policy для scope, а не ограничение модели/effort чата; явный выбор пользователя имеет приоритет. Для Core используй [model-routing](C:/Users/Ant/Documents/Codex/AE_Agent_Core/docs/model-routing.md) для границ credentials и AGY availability. MCP registration и `agy-bridge` executor profile — разные настройки; Core не provisioned source-bound profile `ae-agent`.

В legacy `AE_agent` и Core действует разрешённый пользователем
маршрут делегирования. Пользователь свободно выбирает любую доступную модель
и effort для чата. Проект не задаёт их default и не ограничивает селектор;
выбранная модель ведёт чат и проверяет результаты. **Sol 6.1/high** — рекомендация
для диспетчеризации. Текущий чат автоматически не переключать; явно выбранный
исполнитель имеет приоритет над таблицей.

| Задача | Исполнитель |
|---|---|
| Статус, один готовый короткий вызов проверки или правки | Диспетчер сам |
| Простое самостоятельное поручение: поиск, извлечение данных, правка по образцу | Luna/high: ae_scout для чтения, ae_operator для правки |
| Scoped реализация, отладка и содержательная техническая валидация | ae_implementer: Sol 6.1/high |
| Сложные взаимодействия компонентов, safety/security/authority и устойчивые дефекты | ae_specialist: Sol 6.1/xhigh |
| Ограниченная правка с ясной приёмкой в категории с подтверждённой пользой Flash | Flash 3.8/configured High через antigravity-cli |
| Архитектура, системные границы, сложное планирование | ae_architect: Sol 6.1/xhigh |
| Особо сложные архитектурные решения или содержательная эскалация после XHigh | ae_architect_ultra: Sol 6.1/ultra |
| Независимое ограниченное review | ae_reviewer: Sol 6.1/high |
| Очень сложная задача после содержательной неудачи Sol 6.1/ultra | ae_escalation: Astra/high |

Повторное разрешение на Flash для подходящей ограниченной AE правки не нужно. Само
обсуждение/изменение маршрута не требует запуска. Перед реальным запуском
прочитай antigravity-cli и его AE reference. Профиль `ae-agent` предусмотрен в legacy config, но пока не provisioned для Core.
Контракт и актуальные ограничения клиента:
C:/Users/Ant/Documents/Codex/AE_agent/docs/model-routing.md (legacy).

Диспетчер передаёт Flash исходный запрос, ограничения, ownership и приёмку,
не выполняя ту же реализацию параллельно. Flash самостоятельно читает материалы,
планирует и исправляет. Модель чата проверяет diff, артефакты и применимые критерии;
не требует отдельного полного ревью после каждой задачи. При неудаче Flash
после сверки процесса и эффектов допустим Sol/high в том же scope. Не ждать
двух исправлений при ясном safety/authority или системном вопросе. Нерешённую
инженерную сложность Sol/high и обычную архитектуру передавать XHigh. Ultra
назначать для особо сложных решений или содержательной эскалации после XHigh.
Astra получает содержательную попытку Sol/ultra, проверенные гипотезы и оставшийся пробел. Прямой архитектурный вызов Astra исключён, кроме
явного выбора пользователя. Недоступность Flash после сверки завершения процесса
допускает выполнение того же scope Sol 6.1/high с записанной причиной.

## Доступность и роли

Точные ID: gpt-6.1-sol, gpt-6-luna, gpt-6-astra, gemini-3.8-flash-high.
Роли и каталоги проверяй по актуальным metadata; TOML и самоотчёт не доказывают
effective model/effort. Уже загруженная роль не меняется от правки её файла;
не переопределяй роль во время работы. Подробности конфигурации/окон и клиентов —
в проектном `docs/model-routing.md`, читать их только при соответствующем вопросе.
Luna получает самостоятельную простую часть; короткий готовый вызов делает
диспетчер. При неоднозначности Luna возвращает вопрос, не берёт архитектуру.
В других проектах сначала читать scoped AGENTS; AE разрешение на Flash туда
не переносится. Terra, paid API, покупка кредитов, смена provider и скрытый
fallback исключены. MCP Antigravity и его права проверяются отдельно.

## Передача задачи и общий runtime

Передавай цель, исходный запрос, scope/файлы, baseline, ownership, разрешённые
действия, критерии и предел результата. Writer должен знать, что работает не
один: сохранять чужие изменения и адаптироваться к ним. Возврат — факты/ссылки,
изменения, проверки, пробелы и configured/runtime model status. Результат
исполнителя принимается родителем по фактическим артефактам и проверкам.

Для монтажа готовых плейсхолдеров группируй самостоятельные части по проектному
`docs/montage-workflow.md`. Один блок может содержать несколько typed plans;
короткое чтение или export не требуют нового исполнителя. Диспетчер принимает
итоговые сцены, исполнитель проверяет изменённые цели; одинаковые неизменённые
промежуточные кадры повторно целиком не просматривать. Полная серверная проверка
и свежесть перед mutation сохраняются при compact ответах.

Не более двух активных помощников суммарно: native agents, AGY и помощники Ultra.
Параллельно — только независимые вопросы/снимки либо непересекающиеся изменения.
Один writer на ресурс. Обычные исполнители не делегируют дальше. Архитектурные
роли Sol/xhigh и Sol/ultra могут получить по одному явно выделенному свободному
слоту для ограниченного read-only помощника; тот не
создаёт агентов. При отсутствии выделенного слота анализ идёт последовательно.

У AE/CEP/UI один контроллер, явно назначенный родителем. Остальные работают
по snapshot без live tools. Передача ресурса после timeout требует проверки
процесса, pending/inflight и фактического read-back. Неизвестную мутацию не
повторять и не передавать занятый ресурс другому исполнителю.

Auth/quota/network/MCP/permissions и ошибки рассуждений — разные причины.
Повышение effort не заменяет исправление доступа; отказ нельзя обходить.
Read-only файловый sandbox сам по себе не блокирует MCP/UI writes, поэтому scope
и серверные gates обязательны. Typed library, search/read/build/propose/dry-run,
confirmation, ownership и read-back сохраняются при любом исполнителе.
