# Аудит повторного использования решений AE Agent

Дата: 11 сентября 2026. Проверенный HEAD: `3bd69eb85ffe355760bcd878c97a3fb9a76c168a`.

Это снимок состояния **до улучшений**. Реализованные изменения и актуальные
ограничения от 12 сентября: [использование базы и измерение расхода](solution-reuse.md).

**Вывод.** Готовые инструменты AE Agent уже используются и избавляют Codex от части повторного написания ExtendScript. Однако добавленная база рецептов пока гораздо слабее связана с обычной работой внешнего Codex, чем предполагает идея «библиотеки готовых решений». Точный процент экономии токенов не измерен. Главная следующая инвестиция — улучшить обнаружение и применение существующей базы, затем измерить результат, прежде чем продолжать массовое пополнение.

Это аудит текущего кода, локальных журналов и нескольких сохранённых трасс Codex. Продуктовый код и проект After Effects не изменялись. Из живых проверок выполнены только status, ping и чтение состояния CEP-панели. Провайдерные проверки использовали локальные заглушки.

Но число записей нельзя представлять как число функций, полноценно испытанных на произвольных пользовательских проектах.

**2. Почему внешний Codex не получает всю пользу базы**

Существуют два разных маршрута:

```text
Codex App → MCP tools/list / tools/call → bridge → AE
                          автоматического поиска recipes здесь нет

CEP Agent или plan_with_ai_agent → внутренний планировщик
  → поиск registry + память + снимок AE → вызов модели → план → исполнение
```

MCP-адаптер объявляет только `capabilities.tools`, обрабатывает `tools/list` и `tools/call`. В текущем каталоге нет `search_solutions` / `get_solution`; адаптер не предоставляет recipes через MCP resources/prompts. Это подтверждено и кодом, и набором инструментов, доступных в текущей задаче.

Поэтому внешний Codex может использовать готовый `create_camera_with_controller`, но само наличие файла с рецептом не заставляет его прочитать этот файл. Для этого нужно отдельное обнаружение: файловый поиск, инструкция навыка или специальный инструмент.

Автоматический поиск библиотеки выполняется в `runAgentPlanLogged`. Внешний Codex тоже может попасть на этот маршрут через `plan_with_ai_agent`, но тогда происходит отдельный вызов настроенного провайдера. Это не бесплатное локальное чтение рецепта и не повод добавлять второй LLM-вызов к каждой простой задаче.

Основания: [mcp-adapter.js](../mcp-server/mcp-adapter.js), строки 151–218; [bridge-daemon.js](../mcp-server/bridge-daemon.js), `runAgentPlanLogged` 6744–6769 и `callToolLogged` 19142.

**4. Три главные технические проблемы**

**Поиск не связывает русские запросы с английской базой.** Воспроизведён поиск через `buildSolutionHintsForPrompt` на 12 парах естественных RU/EN запросов, без обращения к модели. По-русски — 0/12 запросов с совпадением. На английских переводах — 12/12.

| Русский запрос | Английский запрос | Есть совпадения RU / EN |
|---|---|---|
| Создай композицию 1920 на 1080 длительностью 10 секунд | Create a basic composition 1920 by 1080 with duration 10 seconds | нет / да |
| Дублируй выделенные слои | Duplicate selected layers | нет / да |
| Создай камеру с контроллером | Create a camera with controller | нет / да |
| Центрируй композицию | Center composition | нет / да |
| Преобразуй текст в фигуры | Create shapes from text | нет / да |
| Зацикли анимацию выражением | Add simple loop expression | нет / да |
| Равномерно распредели ключи по длительности слоя | Distribute selected keyframes evenly across layer duration | нет / да |
| Переименуй выделенные слои по номерам | Rename selected layers with numbers | нет / да |
| Поставь маркеры в начале и конце рабочей области | Add markers at work area start and end | нет / да |
| Добавь выделенные композиции в очередь рендера | Add selected compositions to render queue | нет / да |
| Покажи активную композицию и выделенные слои без изменений | Summarize active comp and selected layers without changing the project | нет / да |
| Установи разностный режим наложения | Set difference blending mode | нет / да |

Это тест обнаружения, а не успешного выполнения. Причина: tokenizer поддерживает кириллицу, но в поисковых полях всех 181 записей нет кириллицы, а сопоставление основано на пересечении слов. Нет перевода, межъязыковых соответствий или поиска по смыслу. Модель может понимать русский, однако поиск выполняется раньше — по исходному запросу.

На английском наличие совпадений тоже не гарантирует релевантность: при запросе создания композиции нужный рецепт оказался третьим после двух рецептов изменения длительности вложенных композиций. При проверке всех точных названий 7 из 181 решений не попали в собственный top-3. Значит, требуется проверка качества ранжирования, а не только целостности JSON.

Основание: [solution-library.js](../mcp-server/solution-library.js), `tokenize:133`, `scoreSolution:234`, `retrieveSolutionHints:342`.

**Подробные алгоритмы рецептов автоматически не загружаются.** Formatter передаёт краткие intent, inputs, preferred tools, key terms и verification summary. Markdown-файлы не читаются; `recipePath` не выводится в итоговую подсказку. Например, формула распределения ключей и порядок сохранения неизменяемых ключей остаются в Markdown, а модель получает главным образом названия входов и общую инструкцию.

Поэтому многие импорты сохраняют полезные знания для ручного поиска и разработки, но ещё не заменяют вычисления модели готовым кодом. Для максимальной экономии такие операции должны становиться параметризованными составными инструментами или детерминированными генераторами плана.

Основания: `solution-library.js:276`, `:451–494`; [пример рецепта распределения ключей](../recipes/ar-distributekeyframestolayer-typed-plan.md).

**Внутренний planner prompt молча обрезается.** Для `Duplicate selected layers`, без снимка проекта и без секции памяти:

| Этап | Символы |
|---|---:|
| Компактный каталог | 14 311 |
| Подсказки решений | 1 568 |
| Полный собранный user prompt | 31 339 |
| После нормализации перед отправкой | 20 000 |
| Отброшено | 11 339 |

Результат независимо воспроизведён выполнением извлечённых функций сборки и нормализации через Node VM, без запуска сервера или провайдера. Специальные правила bulk duplication, deep duplicate и поздние инструкции result bindings не входят в отправляемую часть.

Причина: `normalizeMessages` использует `compactString(args.prompt, 20000)`, а `compactString` — обычный `trim().slice(...)`. AE-планировщик явно устанавливает `messages:undefined`, поэтому альтернативная передача массива сообщений этот маршрут не спасает. Нормализация общая для CLI и API-провайдеров.

Это реальный дефект полноты контекста, а не доказательство обхода защиты: серверная валидация и execution gates продолжают работать. Но недополученные инструкции способны привести к плохому плану, отказам и дополнительным попыткам. Текущий prompt smoke проверяет наличие нескольких ранних секций, но не сохранность конца запроса.

Основания: [bridge-daemon.js](../mcp-server/bridge-daemon.js), `buildAePlanPrompt:6538`, вызов провайдера `:6764–6774`; [ai-agents.js](../mcp-server/ai-agents.js), `compactString:61`, `normalizeMessages:1350`, общий вызов `:1828`; [smoke](../scripts/prompt-optimization-smoke.js), строки 456–510.

**5. Сколько токенов это экономит**

Честный ответ: **положительный эффект повторного использования инструментов есть, но его размер и чистый эффект библиотеки не измерены**. Код готовой операции исполняется локально, и модель может передать короткие аргументы вместо написания полноценного JSX. Однако итог зависит от цены обнаружения, размера ответа, количества инспекций, ошибок и повторных вызовов.

Измеренные объёмы, которые не следует путать с биллингом:

| Объект | Размер |
|---|---:|
| Полный registry на диске | 1 388 330 байт |
| Выдаваемые MCP schemas: `JSON.stringify(exposedTools())` | 165 415 символов |
| Те же tools до добавления общих полей защиты | 110 745 символов |
| Компактный каталог внутреннего planner | 14 311 символов |
| Секция solution hints на 12 EN запросах из таблицы | 1 568–3 169 символов |
| Секция при отсутствии RU-совпадений | 488 символов |

Registry не отправляется целиком — это полезная оптимизация. При условном `chars/4` полный MCP schema JSON — около 41,4 тысячи token-equivalent, compact catalog — 3,6 тысячи, hints — 392–792. **Это только приближение размера текста, не фактические токены модели и не расход каждого сообщения Codex.** Форма сериализации, отложенная загрузка инструментов и кэширование зависят от клиента; поведение CEP planner нельзя автоматически переносить на Codex App.

OpenAI описывает загрузку инструментов по необходимости как способ сократить контекст, одновременно отмечая дополнительные затраты на обнаружение. Документация API не доказывает, как именно текущая версия Codex App учитывает этот конкретный каталог. [Официальная документация tool search](https://developers.openai.com/api/docs/guides/tools-tool-search).

Существующий [tool-token-savings-estimate.md](tool-token-savings-estimate.md) прямо обозначает свои диапазоны как инженерную оценку. Числа вроде 6–16 тысяч сэкономленных токенов за deep duplicate нельзя считать результатом проведённого A/B-теста. Указанная там оценка полного каталога около 34 тысяч также отличается от текущего замера exposed schemas. Документ не является фактическим счётчиком экономии.

Провайдерный слой умеет возвращать `usage`, а панель — учитывать его. Но события `plan_finished` сохраняют количество подсказок, шагов, время и repair-флаги без связки «какое решение выбрали → что выполнили → сколько usage потребовалось». Даже сумма usage сама по себе не даёт экономию без сопоставимого сценария без библиотеки. Тарифные пересчёты из старой оценки в этом аудите не использовались.

**6. Что улучшать в первую очередь**

| Приоритет | Изменение | Проверяемый результат |
|---|---|---|
| 1 | Исправить сборку и ограничение planner prompt: общий обязательный минимум, правила только нужных инструментов, явный бюджет, отсутствие молчаливого отсечения | Критические инструкции доходят до provider payload при коротких и больших снимках; проверяется конец запроса |
| 2 | Предоставить внешнему Codex локальные `search_solutions` и `get_solution` без второго LLM-вызова | Codex находит решение, получает его ID, входы, ограничения и нужные schemas в нескольких компактных шагах |
| 3 | Добавить русские aliases/intents и улучшить ранжирование по действию и объекту | Естественные RU/EN запросы находят нужное решение в top-1/top-3; несовместимые действия не вытесняют нужное |
| 4 | Дополнить рабочий AE-навык порядком: найти готовое → inspect → применить → read-back; raw только при конкретном пробеле | В трассах видно осознанное использование базы и причину fallback |
| 5 | Перенести частые вычислительные рецепты в составные tools / plan builders | Модель передаёт параметры; распределение ключей, массовые замены и аналогичная механика вычисляются кодом |
| 6 | Ограничивать объём инспекции и ответов задачей; повторно использовать ещё актуальные данные в пределах операции | Меньше лишних `get_layer_details`, сериализации и повторного контекста без потери проверки результата |
| 7 | Добавить telemetry применения и A/B-набор реальных задач | Измеряется стоимость успешной задачи, а не количество записей или подсказок |

Для измерений стоит сравнить одинаковые задачи и начальное состояние AE в трёх вариантах: общий raw bridge, текущие typed tools без registry, typed tools с улучшенным retrieval. Фиксировать модель и настройки; разделять входные, кэшированные входные и выходные токены; включать неудачные попытки и отдельные planner-вызовы. Критерии — успешность, время, количество исправлений и usage на успешно выполненную задачу.

Набор должен включать простые операции, распределение ключей, работу с precomp, поиск/замену параметров в шаблоне и пакетные изменения. Это позволит отделить пользу уже существующих typed tools от добавочного эффекта импортированных рецептов.

До исправления первых пунктов массовый импорт новых рецептов имеет неопределённую отдачу. Уже накопленную базу удалять оснований нет: она полезна как материал для поиска, разработки и дальнейшей упаковки. Но критерием успеха следующего этапа должно стать применение решений в обычных задачах, а не рост их количества.
