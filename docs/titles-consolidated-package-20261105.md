# Titles — сводный пакет правил и наработок

5 ноября 2026. Пакет для работы над Titles на MSI и десктопе. Он сводит правила из Titr Builder, документы AE_agent и действующий контракт Core. Решения ниже задают общий порядок для будущей работы. Точные схемы, допустимые цели и полномочия на исполнение определяет соответствующий контракт Core.

## Выбор сценария

| Задача | Что используем | Что проверяем |
| --- | --- | --- |
| Заменить текст на существующем слое с сохранением стиля | Внешний Titles 0.1 и `titles-current-target / set-current-text`. Одна непустая строка, точные `projectId`, `compId`, `layerId`, статичный однородный Source Text | Совпадение цели, исходного текста и revision. После исполнения — новый текст и полное совпадение защищённого профиля стиля |
| Разобрать исходник и подобрать оформление нового титра | Предметные правила Titr Builder, описанные ниже. Результат подготовки — вариант текста, рубрики, разбивка и параметры размещения с объяснением выбора | Сохранение содержания, соответствие профилю, границы в координатах композиции и фактический вид кадра. Изменение стиля, создание слоёв и пакетная сборка требуют отдельных допущенных операций |
| Переключить вариант, перенести эффекты или выпустить видео | Отдельные действия с конкретными объектами, собственными входами, разрешениями и результатами | Идентичность варианта, его видимость и фазы. Для выпуска — terminal receipt, восстановление временно изменённых состояний, проверка файла и изображения |

В задаче сначала фиксируем нужный сценарий. Если пользователь просит изменить только текст, текст передаётся точно, включая Unicode. Подготовка рубрик и нормализация возможны в сценарии оформления, где пользователь видит итоговый текст до применения.

## Разрешённые противоречия

| Где расходились прежние инструкции | Единое правило для пакета |
| --- | --- |
| «Всегда в кавычках» и «сохранить явно написанное название без кавычек» | В профиле прежней серии рубрика названия набирается прописными. Распознанное цитатное название оформляем `«…»`. Явно выделенное или уверенно распознанное название без кавычек сохраняет отсутствие кавычек. Для неразобранной структуры, непарной кавычки или отсутствующего названия показываем ошибку на preview. Пустое `«»` запрещено. |
| Одна строка Core и один многострочный слой Titr Builder | Это два разных контракта. Многострочный слой с рубриками — результат оформления. Setter 0.1 принимает однострочный ввод и защищает прежний стиль. |
| `1.28 × topFont`, равный кегль и правило о сопоставимом весе автора и названия | `Normal` допускает калиброванный акцент названия. При слишком мелкой верхней рубрике сначала проверяем переносы и подходящий профиль, затем уменьшаем акцент. `Equal` выравнивает кегль при сохранении остальных правил выбранного профиля. Значения из примеров относятся к их профилям. |
| Общая композиция, фиксированный `titr`, четыре заданные координаты, ровно 11 слоёв | Композицию задаёт конкретная работа. Читаем актуальные направляющие или явно заданный контейнер. Количество титров берём из валидного задания. Имя композиции, координаты, нумерация и 11 элементов из прежней серии остаются параметрами её шаблона и контрольного примера. |
| «Гайды задают жёсткую рамку» и подстановка координат старым `readGuides` | Ожидаем однозначно определённые границы по осям или явно заданную рамку. При неполных или неоднозначных направляющих показываем причину остановки. Исторический fallback по сортированным позициям и фиксированным координатам учитываем как поведение старой панели. |
| «Поставить position в центр» и «визуально центрировать текст» | Центр точки слоя — отдельная геометрическая операция. Для fit считаем полные видимые bounds в координатах композиции на выбранном кадре. После геометрического read-back оцениваем видимые поля, баланс и clipping на изображении. |
| Пересечение измеренных прямоугольников и требование читаемых интервалов | Leading относится к следующей строке пары. Сравниваем границы относительно baseline. Допуск на перекрытие измерительных bounds применим к конкретному калиброванному профилю при видимом отсутствии касания глифов. |
| Новый слой виден в таймлайне, а выбранный вариант нужен в кадре | Создание серии, просмотр и выпуск — разные фазы. У старой панели новый титр по умолчанию имеет `shy=false` и `enabled=false`. Для вариантов одного шаблона подходит общая текстовая композиция, если задание допускает общий контейнер. В preview/render явно выбираем вариант и читаем эффективную видимость. Изменять `enabled`, `shy` и свойства композиции можно в рамках заявленного действия, а старые слои скрывать только при подтверждённой принадлежности к управляемой серии. |
| Старый helper скрывает весь прочий текст, а локальный `SKILL.md` ограничивает область своей серией | Для Core принимаем узкое правило владения. Похожие имена, префиксы, возраст или соседство слоёв сами по себе не доказывают принадлежность. `setTimelineVisibility` из JSX не переносим напрямую. |
| Скрипт берёт маркер с первого подходящего текстового слоя и заменяет маркеры получателей | Если эффект зависит от маркера, назначаем источник и целевые слои явно. Проверяем комментарий и время нужного маркера. Слияние и замена — разные действия. Существующие пользовательские маркеры сохраняем по умолчанию. |
| Прямой Build из ScriptUI и Core с подтверждением | Прямой Build описывает UI старой панели. В Core путь записи проходит typed inspection, server build/proposal, dry-run, применимое подтверждение и read-back. Старый GUI fallback относится к разрешённому тогда эпизоду. |
| Скриптовый Verify, PNG review, native read-back и DONE рендера | У каждого результата свой статус. Старый `verifyAutoTitles` сообщает count и проверяет геометрию и флаги слоя. Количество по заданию и правильность разбора проверяем отдельно. Геометрия, native состояние, просмотр кадра и готовый медиафайл имеют собственные критерии. |

## Правила подготовки и вёрстки

1. **Вход.** Сохраняем исходный текст и отдельно формируем представление для оформления. При подготовке рубрик можно нормализовать пробелы, парные кавычки и внешние маркеры. Внутренние дефисы и смысловые части текста сохраняем. Сначала распознаём нумерованные блоки, включая один блок. Затем проверяем границы по пустым строкам. Если их нет, используем разбор по строкам с отметкой неоднозначности. Авторы, пояснение и название получают явные роли. В прежнем профиле инициалы компактные, авторы разделяются запятыми, пояснение после списка авторов получает собственную рубрику. Перенос внутри незакрытой цитаты объединяем, когда он действительно продолжает одну рубрику. Имена и специальное форматирование из прежних работ используем для проверочных случаев или явно выбранного профиля.
2. **Базовый вариант и альтернативы.** Сначала оцениваем исходную разбивку. При нехватке места, мелкой верхней рубрике или пустующей высоте рассматриваем разбиение названия, списка авторов и длинного пояснения. Разбиваем по границам слов и смысловых групп. Сохраняем короткую двухстрочную форму, когда она уже читаема. При сопоставимых вариантах предпочитаем более полную верхнюю строку. Ручной перенос фиксируем как локальный override с пересчётом только данного титра.
3. **Профиль.** Кегль, tracking, обводка и интервалы определяются ролью, плотностью, доступным контейнером и выбранным профилем. Строки одной рубрики сохраняют согласованный размер. Tracking следует профилю. Пределы около 70 px, плотный вариант около 64 px, коэффициент 1.28 и старые допуски gaps служат калибровочными ориентирами для соответствующих условий. Для новой геометрии сверяем визуальный размер и читаемость на реальном кадре.
4. **Измерение.** Используем фактический шрифт, стиль, stroke, tracking и leading. Измеряем границы относительно baseline. Учитываем frame, время, anchor и преобразования слоя. Если вложенность, родитель, поворот, перспектива или эффект меняют видимый результат, нужна поддерживаемая проекция либо явный статус неподдерживаемой геометрии. При неизвестном шрифте или недоступном требуемом поле фиксируем причину.
5. **Fit.** Сначала подбираем типографику, затем применяем равномерный X/Y scale к допустимому текстовому слою, если сценарий разрешает эту запись. Для прямоугольной модели масштаб ограничивают обе оси frame, с калиброванным запасом. Центрируем измеренные границы и заново проверяем полную геометрию. Из допустимых альтернатив выбираем по видимому размеру, иерархии, заполнению и читаемости. Лимит кандидатов и стабильный порядок нужны для повторяемости. Если допустимой альтернативы нет, возвращаем объяснение, какой критерий не выполнен.
6. **Приёмка кадра.** Сверяем фактический текст, count из задания, принадлежность слоёв, enabled/shy в нужной фазе, frame и места возможного наложения. Смотрим изображение в читаемом размере. Для анимации выбираем кадры, покрывающие важные состояния, включая видимую фазу входа/выхода, если они входят в задание. Допуск геометрии фиксируем в профиле, а художественную оценку относим к фактически просмотренным кадрам.

## Точная граница действующего Core

- `compile` возвращает намерение. `prepareBuild` сверяет совместимость публичного контракта, точную цель и структуру несинтетической inspection. Core сам проверяет подлинность и свежесть evidence, строит серверный план и связывает его с целью, preimage и revision. [Compiler](../products/titles/src/compiler.js), [job schema](../products/titles/job.schema.json), [контракт](../core4/modules/titles-current-target/contract.json), [порядок работы](../products/titles/WORKFLOW.md).
- `titles-current-target` проверяет 13 полей символа и 3 поля абзаца, однородность текста и отсутствие анимированного Source Text. `titles_missing_stroke_color` был наблюдён на двух исторических native-целях. Код отказа означает отсутствующее или `null` поле и сам по себе не устанавливает причину. Сохраняем полный профиль. Включение обводки для чтения, подстановка RGB, пропуск поля или переход на соседний модуль не подходят как восстановление прежней гарантии. [Executor](../core4/modules/titles-current-target/executor.jsx), [R5](../plans/core4-titles-inspection-20261101.md#завершение-на-паузе--строгий-профиль-сохранён).
- `titles / set-text` и `titles-current-target / set-current-text` имеют отдельные контракты и политики исполнения. Для Titles 0.1 используем второй. Product compiler остаётся слоем подготовки поверх существующего контроллера. `recordContext` описывает цель и время жизни записи. При UNKNOWN сначала выясняем исход первоначальной команды. [Архитектурная граница](../plans/external-products-titles-20261029.md#принятая-граница), [recordContext](record-context.md).
- Независимое native-чтение базы на обеих машинах прошло для выбранного manual/owner scope. Приёмка Titles 0.1 на реальной целевой композиции и две проверки `titles-owner` / `titles-executor-contract` остаются отдельными этапами. T1 offline и прежние R5 результаты сохраняют своё исходное покрытие. [Двухмашинный итог](core-portability-final-two-host-result-20261104.md), [manifest](core-release-manifest-20261103.json).

### Очерёдность при продолжении разработки

1. **Сначала узкая проверка 0.1.** После возобновления T2 использовать явно выбранную тестовую цель с наблюдаемым полным профилем. Получить новую inspection и выполнить один штатный сценарий по контракту. Сверить текст, защищённые поля, receipt и кадр. Missing-field возвращает работу к выбору поддерживаемой цели или отдельному проектированию контракта.
2. **Затем чистая подготовка вёрстки.** Выделить из Titr Builder parser и генерацию кандидатов, оставить профили как данные. Синтетическими примерами покрыть явное название без кавычек, нераспознанную структуру, длинное пояснение, удачные две строки, override одного титра и неподдерживаемую геометрию. Сохранить сравнение с прежними калиброванными примерами без переноса пользовательских текстов.
3. **Измерение, применение и визуальная проверка.** Спроектировать узкие операции под первый выбранный сценарий. Покрыть реальными измерениями простой 2D frame, а дополнительную геометрию добавлять по подтверждённой потребности. Проверить изменения только на точных целях и сохранить фактические bounds и кадры. Раздельно учитывать source, VM, native и визуальное покрытие.
4. **Варианты, эффекты, экспорт.** Возвращать отдельно по рабочему запросу. Переиспользовать из legacy структуру проверки варианта и результата. Для каждого нового или изменённого модуля проверить упаковку, обнаружение локальной среды и необходимые части пути MSI ↔ десктоп. [Правило переносимости](portability.md#новые-модули-и-последующие-версии).
