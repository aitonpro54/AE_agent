# Tool-First / MCP-First рабочий процесс и минимизация Computer Use

## Цель и принципы

Основным способом взаимодействия агента с Adobe After Effects является **Tool-First / MCP-First** подход:
вызов типизированных MCP-инструментов, переиспользование проверенных решений из реестра и выполнение
планов через bridge-сервер и CEP-панель.

Прямое управление графическим интерфейсом (**Computer Use / GUI-clicking**) переводится в статус
строгого резервного механизма (**fallback**).

Ожидаемые измеримые преимущества:
1. Сокращение экранного времени и перехватов фокуса/курсора у пользователя.
2. Переход к детерминированным последовательным типизированным пакетам (sequential typed batches) под контролем единого контроллера (one controller on resource).
3. Снижение сетевых накладных расходов за счёт исключения передачи регулярных скриншотов рабочего стола при наличии типизированных инструментов.

## Канонический маршрут Tool-First

Любая операция изменения проекта или структуры композиций следует строгому циклу:

```
search_solutions ──> get_solution ──> build_solution_plan ──> propose_ai_agent_plan
                                                                      │
PNG-view <── readback <── run_ai_agent_plan <── dry-run (run dryRun:true) <──┘
```

1. **`search_solutions`**: Поиск готового параметризованного рецепта по ключевым словам и задаче.
2. **`get_solution`**: Чтение конкретной спецификации шагов и контракта параметров без загрузки всего реестра.
3. **`build_solution_plan`**: Построение типизированного плана изменений с валидацией входных аргументов.
4. **`propose_ai_agent_plan`**: Регистрация предложения с фиксацией неизменяемых меток (**immutable proposal pins**):
   - `actionId`
   - `instanceId`
   - `revision`
5. **`validate_ai_agent_plan` и Dry-run**:
   - `validate_ai_agent_plan` выполняет предварительную статическую проверку структуры плана и аргументов (preflight), но **не является квитанцией dry-run**.
   - Фактический dry-run выполняется сервером через вызов `run_ai_agent_plan(dryRun: true)` с сохранением текущих меток предложения и полной идентичности плана.
6. **`run_ai_agent_plan`**: Исполнение плана через bridge (при включённой автономной сессии или подтверждении в CEP).
7. **`readback`**: Обязательная независимая вычитка изменённых свойств и сущностей (`get_comp_details`, `get_layer_details`, `get_property_value`). Успешный HTTP/MCP транспорт не заменяет фактическую проверку состояния AE.
8. **`PNG-view`**: Экспорт контрольного кадра (`save_comp_frame_png`) и **фактический визуальный просмотр** полученного изображения.

### Пассивные ожидания состояния (Passive Waits)

Для наблюдения за завершением операций панели или bridge используются типизированные инструменты пассивного ожидания:
- `wait_for_bridge_state` — мониторинг статуса соединения панели (`connected`, `idle`).
- `wait_for_plan_state` — мониторинг перехода состояния proposal (`superseded`, `expired`, смена `stateToken`).

**Правила пассивного ожидания**:
- Опрос происходит исключительно по локальным in-memory данным bridge-сервера (`waitMs` в пределах 0..30000 мс, строго целое число).
- Запрещены активные вызовы AE, HTTP-запросы наружу, обращения к LLM и мутации проекта внутри цикла ожидания.
- Метки ожидания (`actionId`, `instanceId`, `revision`) служат исключительно для наблюдения и **никогда не дают прав на исполнение мутаций**.

## Таксономия причин отката к Computer Use (CU Fallback Taxonomy)

Использование GUI-кликанья и Computer Use допустимо **только** при наличии явной классифицированной причины
из следующего фиксированного списка:

| Причина | Описание | Допустимое действие |
|---|---|---|
| `typed_gap` | Требуемая операция отсутствует в типизированных MCP и не может безопасно выполняться существующими CLI, helpers или API. Функции собственной CEP-панели не являются typed_gap: они вызываются через `invoke_panel_action` / CLI. | Точечное действие в GUI сторонних элементов с фиксацией пробела для последующей типизации. |
| `visual_ui_only` | Взаимодействие с элементами сторонних плагинов или окнами настроек, не имеющими программного ExtendScript/DOM API. | Навигация и клик по специфичным UI-элементам стороннего расширения. |
| `panel_bootstrap` | `ensure_ae_agent_panel` и штатный CLI/API путь подтверждённо недоступны; установлен настоящий UI-only blocker. `panelConnected=false` само по себе не доказывает закрытую панель. | Ограниченное открытие окна панели через меню `Window -> Extensions` после проверки typed bootstrap; работающий штатный путь исключает GUI opening/reload. Любые действия внутри уже открытой панели производятся программно без CU. |
| `protected_confirmation` | Действие требует интерактивного подтверждения пользователем в UI панели в соответствии с политикой безопасности M100. | Ожидание клика пользователя либо подтверждение по явной команде. |
| `modal_blocker` | Появление системного диалогового окна ОС или предупреждения After Effects, блокирующего командный интерфейс Bridge. | Закрытие или подтверждение блокирующего диалога. |
| `diagnostics` | Расследование сбоя отображения UI панели или графического артефакта, когда логи и типизированные инструменты не дают ответа. | Ограниченный снимок экрана для анализа ошибки интерфейса. |

> [!IMPORTANT]
> **Исключение функций CEP-панели из Computer Use**:
> Нажатие кнопок, переключение вкладок, настройка провайдеров, управление сессиями и запуск действий внутри собственной
> CEP-панели осуществляются исключительно программно через MCP-инструменты `list_panel_actions`, `get_panel_state`,
> `invoke_panel_action`, `get_panel_action_result` либо CLI `node scripts/cep-panel-control.js`.
> Подробности: [Программное управление CEP-панелью](cep-panel-programmatic-controls.md).
> Программный control не открывает/перезагружает панель автоматически. Missing assets/service/CDP —
> явная недоступность. При `unknown` читать исходный receipt и exact-run evidence; новый UUID,
> `idle` или отсутствие очереди не снимают guard и не разрешают replay.

### Завершение ограниченного блока Computer Use

Перед первым действием кратко зафиксируй точную цель UI-блока. Сразу после последнего
необходимого действия перечитай результат и сверь все отправки с неизвестным исходом
по доступному read-back; не повторяй их вслепую. Затем заверши UI-блок до перехода к
офлайн-редактированию, ожиданию Flash, тестам или длительным пассивным ожиданиям.

Сначала сохрани нужные компактные наблюдения в обычной задаче или записи evidence,
затем в том же REPL единственного контроллера вызови поддержанный
`mcp__node_repl__js_reset`, чтобы очистить его JavaScript kernel и bindings. Не сбрасывай
REPL другого контроллера. Этот reset сам по себе не подтверждает закрытие Codex CU
overlay и не доказывает освобождение компьютерного контроллера: фиксируй отдельно
«UI-действия завершены / JS-среда сброшена» и «управление освобождено» только при
наблюдаемом подтверждении runtime или UI. Если нет документированного способа
освобождения либо badge остаётся, сообщи об этом прямо; при видимом badge пользователь
может закрыть overlay вручную клавишей Esc или использовать документированные элементы
остановки/перехвата управления ([официальная справка Computer Use](https://learn.chatgpt.com/docs/computer-use)).
Не отправляй Esc программно в Codex UI.

Не используй недокументированные API, скрытые протоколы, завершение процессов или новые
зависимости для закрытия overlay. CEP не может объявлять состояние Codex CU без
авторитетного источника; не создавай фиктивный индикатор и не связывай это состояние с
режимом автономной сессии CEP или подключением bridge. Все действующие категории и gates
таксономии выше сохраняются.

## Штатная диагностика и reload CEP

Первый путь открытия/восстановления — typed `ensure_ae_agent_panel({timeoutMs:30000})`.
Он самостоятельно проверяет pending/inflight/lifecycle, точную установленную
панель и единственный уже запущенный AE; connected path делает обычный native
`get_project_info` без reload. Disconnected path использует exact CDP page reload
либо независимый фиксированный `AfterFX.exe -r` bootstrap. Success требует
panel connection и настоящего typed read, timeout/unknown нельзя повторять
вслепую. Authority, условная ExtendScript поддержка и reconciliation описаны в
[контракте bootstrap](ae-agent-panel-bootstrap.md). Отсутствие связи не доказывает,
что панель закрыта. Новый инструмент не отключает auth/confirmation gates.

Перед reload получи свежий `get_bridge_status`: `pendingCommands=0`, `inflightCommands=[]`, нет незавершённого исполнения. Если результат ранее отправленной операции неизвестен, сначала сверь её судьбу; сам по себе `activeEditSession` не запрещает reload панели. Для daemon restart действуют отдельные ограничения.

Штатный helper сам проверяет `http://127.0.0.1:8870/json/list`: должна быть ровно одна ожидаемая page с точным extension root AE Agent и пригодным WebSocket URL. При отсутствии, чужой или неоднозначной цели команда останавливается до подключения; запасного выбора первой страницы нет. Для диагностики можно отдельно прочитать этот endpoint, не выполняя reload.

Из корня репозитория выполни штатную команду, отключив автостарт daemon:

```powershell
$env:CEP_PANEL_ENSURE_DAEMON='0'; node scripts/cep-panel-cdp-smoke.js reload
```

После reload проверь `state.status`/`state.badge` в результате CLI (Connected/online), затем `get_bridge_status` с `panelConnected=true` и настоящий typed `get_project_info`. Computer Use для reload допустим только после подтверждения отсутствия или недоступности штатного CLI/CDP пути. Отказ gate не является пробелом инструмента и не обходится GUI.

## Защитные инварианты и правила безопасности

1. **Отказ Gate не является поводом для обхода (Gate Refusal Is Never Bypassed)**:
   Если dry-run (`run_ai_agent_plan(dryRun: true)`), risk policy или approval gate отклоняет операцию или требует подтверждения,
   **категорически запрещено** пытаться обойти отказ через Computer Use, клики мыши или raw script. Отказ означает
   необходимость корректировки параметров плана или согласования с пользователем.

2. **Обязательность фактического визуального подтверждения (Visual Proof Requires Actual View)**:
   Экспорт изображения через `save_comp_frame_png`, `node_repl` или CUA-экспортёр сам по себе **не является**
   доказательством корректности кадра. Агент обязан фактически просмотреть изображение (через доступные механизмы просмотра артефактов)
   и оценить визуальную иерархию, выравнивание, поля и отсутствие артефактов перед сдачей этапа.

3. **Разделение прав наблюдателя и исполнителя (Observer Pins vs Execution Authority)**:
   Инструмент `wait_for_plan_state` принимает 3-полевой кортеж наблюдателя (`actionId`, `instanceId`, `revision`).
   При несовпадении любого из полей план сразу возвращается как `superseded` или `absent`.
   Для фактического исполнения план обязан сохранять полную идентичность и защитный хеш политики (`policyHash`),
   проходя полную цепочку preflight и dry-run валидации.

## Визуальный аудит композиций (Comp Visual Review Plan & Manifest)

Для многокадрового визуального аудита без ручного управления GUI и без захвата экрана через Computer Use используются специализированные инструменты:

### 1. `build_comp_visual_review_plan`

Генератор типизированного плана экспорта контрольных кадров:
- **Входные аргументы**: `{ targets: [{ compItemId: number, times: number[] }] }`.
- **Строгие ограничения**: не более 4 композиций, не более 12 суммарных кадров, не более 18 шагов в итоговом плане.
- **Безопасность**:
  - Строгая валидация входных данных до отправки запросов в AE.
  - Опрос `get_project_info` и `get_comp_details(includeLayers: false)` по устойчивым `compItemId`.
  - Сверка актуальности проекта (file path, revision) для защиты от устаревания (stale project).
  - Генерируемый план содержит исключительно шаги `save_comp_frame_png` с детерминированными именами файлов `comp-review-<UUID>-<ordinal>.png` в доверенном каталоге экспорта.
  - Сам построитель плана является read-only, но формируемый план экспорта является защищенным мутирующим (`execution.mutating: true`), требующим явного подтверждения (`confirm: true, allowMutations: true`) при выполнении через `run_ai_agent_plan`.

### 2. `get_comp_visual_review_manifest`

Инструмент проверки и формирования манифеста фактических результатов визуального аудита:
- **Входные аргументы**: строго `{ runId: string }` (UUID серверной записи исполнения плана без приведения типов и лишних полей).
- **Проверка на стороне сервера**:
  - Чтение записи исполнения `ae-agent-plan-run-record.v1` из журнала сервера.
  - Строгая валидация структуры builder-плана (4..18 шагов, непрерывная нумерация ординалов 1..N, единый UUID, до 12 кадров, до 4 уникальных композиций, post-read проверки).
  - Проверка containment путей файлов: запрещены ссылки за пределы корня экспорта (`..`, абсолютные пути вне root, symlink escape).
  - Проверка фактического наличия файлов на диске, размера, валидности PNG сигнатуры и расчет SHA-256.
  - Статус `complete` возможен только при успешном завершении (`run.dryRun === false, run.ok === true, failedCount === 0`, наличие `finishedAt`). При dry-run, ошибках или повреждении возвращается `incomplete` или `corrupt`.
- **Обязательные инварианты манифеста**:
  - Манифест всегда возвращает явные фиксированные флаги:
    - `historicalCapture: true` (подтверждает только исторический факт сохранения кадров в момент выполнения плана).
    - `currentProjectStateVerified: false` (не гарантирует, что текущий проект в AE не был изменен после экспорта).
    - `canonicalFreshness: false` (не гарантирует свежесть относительно последующих правок).
    - `artisticAccepted: false` (манифест не подменяет собой художественную приёмку человеком или визуальный анализ модели).

## Нативное чтение состояния проекта (`get_project_lifecycle_state`)

Инструмент `get_project_lifecycle_state` предназначен для легкого чтения состояния проекта в After Effects:
- **Аргументы**: строго 0 аргументов.
- **Возвращаемые данные**:
  - `file`: путь к проекту или `null`, если проект не сохранен.
  - `projectPresent` и `revision`: точные значения или `null`, если AE getter недоступен.
  - `dirty`: булев флаг наличия несохраненных изменений в проекте (`app.project.dirty`).
  - `appVersion`: версия только если native getter поддерживается; иначе `null`.
  - `supported`: отдельный флаг достоверности для `appVersion`, `file`, `dirty` и `revision`.
  - `lifecycleReady` и `reasons`: named source и причины отказа от перехода.
  - `lifecycle.enabled`, `blocked`, `problem`, `pending`: runtime opt-in и защита store.
  - `observedAt`: временная метка наблюдения.
- **Инварианты**:
  - Строго read-only: 0 записей в проект, 0 мутаций таймлайна или композиций.
  - При ошибке выполнения скрипта возвращается явная ошибка чтения (`ok: false`).

## Именованные переходы проекта

`guarded-project-lifecycle` описан в [рецепте lifecycle](../recipes/project-lifecycle.md).
Доступность зависит от фактического состояния daemon: перед операцией прочитай свежий
`get_project_lifecycle_state` и требуй `enabled === true`, `blocked === false`,
`problem === null`, `pending === null` и готовый protection store; не выводи состояние
из версии панели, предыдущего acceptance или настроек проекта. Live acceptance и его
границы записаны [отдельно](tool-first-live-acceptance-2026-10-05.md). Подключённый
recipe forwarding строит тот же план через
`build_solution_plan` с `solutionId: "guarded-project-lifecycle"`; прямой typed
builder — `build_project_lifecycle_plan({operation, targetProjectFile, checkpointLabel})`.
Разрешены только single-step Save As/open/create планы с exact CEP manual confirmation;
неизвестный исход требует read-only reconcile, никогда replay. Это high-risk переход,
который меняет Undo и активный контекст проекта. Для полного media/proxy read-back
проверяй actual item kind/path и cross-relations; текущая corrected acceptance и
принятая scoped CEP current-plan refresh/adoption проверка описана в acceptance note. Там также
зафиксирован один protected-placeholder отказ до плана; это узкий кейс, не общая
гарантия `/hooks` enforcement.

## Проектный PreToolUse Guard и перехват Computer Use

Для предотвращения несанкционированного использования Computer Use (включая попытки GUI reload панели, GUI сохранения или создания слоёв в обход типизированных инструментов) реализован проектный синхронный перехватчик `PreToolUse`.

### 1. Архитектура и перехватываемые инструменты

Перехватчик реализован в [scripts/ae-tool-first-pretool.js](../scripts/ae-tool-first-pretool.js) и подключается через проектный файл `.codex/hooks.json`:
- **Контролируемые каталожные имена**:
  - REPL: `mcp__node_repl__js`, `mcp__node_repl__js_reset`, `mcp__node_repl__js_add_node_module_dir`, `mcp__cua_repl__js`, `mcp__cua_repl__js_reset`.
  - Shell: `Bash`, `exec_command` (блокируются прямые вызовы `@oai/sky`, `codex-computer-use` и CLI-манипуляции мышью/клавиатурой в обход утвержденного CLI).
- **Канонический Project Scope (realpath containment, sibling-safe)**:
  - Проверяется строгое нахождение рабочего каталога (`cwd`) внутри корня проекта через `fs.realpathSync`.
  - Sibling-каталоги с похожим префиксом (например, `AE_agent_backup`) и внешние вызовы пропускаются без ограничений (`pass`).
  - При отсутствии или невозможности канонизации `cwd` вызов блокируется по принципу **fail-closed** (`deny`).
- **Синхронный контракт deny/pass**:
  - `deny`: возврат JSON `{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny","permissionDecisionReason":"..."}}` на stdout с кодом завершения `0`.
  - `pass`: код завершения `0` без вывода на stdout.
  - Любая ошибка парсинга или поврежденный входной payload (включая `[]`, отсутствие обязательного `tool_name` или невалидный JSON) блокируются по принципу **fail-closed** (явный `deny`).

### 2. Контракт Fallback Packet

Любой вызов CU-capable REPL обязан содержать компактный декларативный пакет отката в формате строгого JSON. Пакет передается либо в существующем поле `title` вызова инструмента, либо исключительно в виде реального первого лексического комментария в начале исполняемого кода (`/* AE_TOOL_FIRST_FALLBACK: {...} */` или `// AE_TOOL_FIRST_FALLBACK: {...}`):

```json
{
  "reason": "panel_bootstrap",
  "primitive": "open_closed_panel",
  "evidence": "cep-connection-closed-evidence-id"
}
```

**Обязательные поля**:
- `reason`: строго одна из 6 утвержденных категорий таксономии (`typed_gap`, `visual_ui_only`, `panel_bootstrap`, `protected_confirmation`, `modal_blocker`, `diagnostics`).
- `primitive`: имя единичной атомарной операции (непустая строка).
- `evidence`: непустая строка ссылки на журнал, состояние или инцидент.
- Для `protected_confirmation`: обязательно наличие строго типизированного объекта предложений:
  ```json
  {
    "proposalPins": {
      "actionId": "act_11111111222243338444555555555555",
      "instanceUUID": "11111111-2222-4333-8444-555555555555",
      "revision": 5,
      "dryRunId": "22222222-3333-4444-8555-666666666666",
      "payloadHash": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
    }
  }
  ```
  `dryRunId` обязан быть строковым UUID (`true` не является идентификатором). Пакет подтверждения **не наделяет полномочиями исполнения** и не подменяет CEP dry-run / confirmation.

### 3. Нормализация клавиатурных комбинаций и безусловный запрет GUI-подмен

Перехватчик нормализует документированные алиасы клавиш вендора (`Control`, `Control_L`, `Control_R`, `Ctrl`, `Cmd`, `Shift`, `Alt`) независимо от регистра, пробелов, порядка и переносов строк в многострочных вызовах `press_key`:
- **`Ctrl+O` / `Control_L+o` / `Open Project`**: безусловно запрещено открытие проектов через GUI независимо от заявленной причины.
- **`Ctrl+N` / `Control+N` / `New Project`**: безусловно запрещено создание проектов через GUI независимо от заявленной причины.
- **`Ctrl+R` / `F5` / `Reload`**: запрещен GUI reload панели; штатный reload выполняется через CLI `$env:CEP_PANEL_ENSURE_DAEMON='0'; node scripts/cep-panel-cdp-smoke.js reload`.
- **`Ctrl+S` / `Save Project As`**: сохранение именованных проектов через GUI запрещено.
- **Исключение начального безымянного сохранения (`first_unnamed_save`)**: комбинация `Ctrl+Shift+S` разрешена в рамках scope `reason: "typed_gap"`, `primitive: "first_unnamed_save"` при декларации в `evidence` свежего безымянного состояния (`fresh unnamed`) и владения фикстурой (`owned fixture`). Сам hook проверяет текст декларации; исполнитель обязан отдельно подтвердить свежий native state и ownership. Для именованных проектов исключение не разрешено рабочим контрактом.
- **`timeline` / `comp_layer`**: манипуляции плейхедом и создание слоев через GUI запрещены.

### 4. Bounded Exemptions (Узкие исключения)

- Инструменты сброса окружения (`js_reset`, `cua_repl__js_reset`) и добавления путей (`js_add_node_module_dir`) без кода выполнения пропускаются (`pass`).
- Исключение read-only canary предоставляется **только** для точного comment-only/no-op шаблона (например, `/* AE_TOOL_FIRST_READONLY_CANARY */ 0;`), без lookup изменяемых REPL bindings. Любой произвольный код с подстрокой canary-маркера или вызовом алиасов контроллера отклоняется.
- Неразмеченный код (включая обращения через переменные-алиасы `sky`, сохраненные в REPL на предыдущих шагах) надежно отклоняется (**alias-safe**).
- Пакет в коде обязан быть реальным начальным комментарием (комментарии внутри строковых литералов отклоняются).

### 5. Ограничения безопасности (Security & Coverage Limits)

- Guardrail является проектным фильтром деклараций и синтаксического анализа известных комбинаций/вызовов, а не всеобъемлющей песочницей виртуализации произвольного JavaScript.
- При аппаратных сбоях запуска процесса перехватчика среда Codex может сработать в режиме fail-open (вызов может пройти).
- Нестандартные или закрытые специализированные пути вызова внешних процессов не объявляются защищенными.

### 6. Установщик и аудит (`install-ae-tool-first-hook.js`)

Управление установкой перехватчика осуществляется скриптом [scripts/install-ae-tool-first-hook.js](../scripts/install-ae-tool-first-hook.js):
- **Режим проверки (`--check`)**:
  Инспектирует `.codex/hooks.json`, рассчитывает контрольный SHA-256 хеш определения хука и выводит текущий статус соответствия без раскрытия секретов.
- **Режим установки (`--install`)**:
  Формирует команду хука с использованием абсолютного пути к текущему исполняемому файлу Node (`process.execPath`) и скрипту в кавычках.
  Владение хуком строго ограничено точной полной командой текущего проекта: сторонние обработчики (в том числе из других проектов с совпадающим именем файла `ae-tool-first-pretool.js` или с дополнительными аргументами) и сторонние группы (включая пустые) строго сохраняются.
  Перед записью выполняется валидация схемы контейнера: при значении `null`, массиве или несовместимой структуре операция прерывается с ошибкой без записи. При отсутствии файла на диске используется начальный пустой объект.
  Атомарная запись через временный файл и переименование.
- **Режим удаления (`--uninstall`)**:
  Удаляет только наш обработчик; если в группе есть сторонние обработчики или группа чужая, она сохраняется.

### 7. Штатный Trust и Desktop Canary

1. После установки из корня проекта проверь соответствие точного локального hook:
   `node scripts/install-ae-tool-first-hook.js --check` читает
   `C:\Users\Ant\Documents\Codex\AE_agent\.codex\hooks.json`, command и hash.
2. Затем проверь `/hooks`: точное текущее определение должно быть `Installed 1`,
   `Active 1 [x]`, `Trust: Trusted`. Если оно уже Trusted, повторное доверие не
   требуется. До review/trust non-managed hook не считается активным; изменение
   definition hash требует нового review/trust. На 2026-10-05 установленный
   definition hash `1e6345f23c5fee924da00458ec416c318d9efee6674091b71e00d867af42ed0d`
   уже прошёл штатный CLI review/trust. См. официальный раздел
   [Codex hook tool coverage](https://learn.chatgpt.com/docs/hooks#tool-coverage).
3. Верификация активного потока (Desktop Canary):
   - Попытка вызова `mcp__node_repl__js` с кодом `throw new Error("AE_TOOL_FIRST_CANARY_EXECUTED")` без fallback-пакета обязана быть отклонена хуком (`permissionDecision: "deny"`) **до** фактического запуска REPL.
   - Read-only canary с точным шаблоном `/* AE_TOOL_FIRST_READONLY_CANARY */ 0;` должна завершиться успешно (`pass`), а запрещённая canary — получить hook deny до исполнения. Для definition hash `1e6345f23c5fee924da00458ec416c318d9efee6674091b71e00d867af42ed0d` после удаления временного observer подтверждены nested `node_repl`, direct `cua_repl` и shell: отрицательные вызовы блокируются; точные no-op проходят для nested/direct, а shell positive control был обычным `WriteOutput`. Это bounded acceptance перечисленных путей, не универсальное покрытие произвольного JS или всех catalog tools; более ранние противоречивые canary и пределы доказательства записаны в [live acceptance note](tool-first-live-acceptance-2026-10-05.md). Trust этого же определения не повторяй.
