# Закрытые AEP: отдельный модуль без обязательной панели

1 ноября 2026. Research по прямому вопросу пользователя; предложение будущего
расширения, не реализация и не разрешение редактировать пользовательские AEP.
Продолжает [панели и переносимость](panel-and-client-portability-20261101.md).

## Какой инструмент найден

По описанию подходит [forticheprod/py-aep](https://github.com/forticheprod/py-aep):
Python-библиотека прямого чтения/изменения/записи бинарного AEP (RIFX), без AE.
[PyPI](https://pypi.org/project/py-aep/) при чтении показывает 0.18.2 от
17 октября 2026. Это найденная публичная версия, не подтверждённая локальная.
Текущая документация default branch может отличаться от конкретного релиза.

Локальное расположение не установлено. Bounded поиск помощника в Documents
(Codex/ChatGPT/GitHub/IncomingFromPC и другие перечисленные им каталоги), нескольких
стандартных Python-каталогах не нашёл пакет. Root дополнительно проверил имена
файлов Desktop/Downloads/Tools и верхние каталоги D:. В PATH обнаружены только
WindowsApps aliases python/python3, без py/uv/pip; aliases не запускались.
Это не доказывает отсутствия другого окружения, копии на другом компьютере
или в непроверенном каталоге. Пользователю отправлен необязательный вопрос о пути.

По [README](https://github.com/forticheprod/py-aep/blob/main/readme.md) и
[quickstart](https://github.com/forticheprod/py-aep/blob/main/docs/quickstart.md)
доступны чтение структуры, изменение свойств и ключей, создание композиций/слоёв,
работа с источниками footage, сохранение нового AEP. Очередь рендера можно
подготавливать, но некоторые операции требуют templates из AE preferences.
Библиотека сама не рендерит и не вычисляет expressions; не все свойства поддержаны.

[Known Limitations](https://forticheprod.github.io/py-aep/limitations/) различает
сохранённое значение и вычисленный результат expression. Для текста возможен
устаревший layout cache; повторное чтение записанного файла не доказывает свежесть
раскладки. Некоторые API используют синтезированные сведения. Поэтому
«записалось и прочиталось» недостаточно для эквивалентности native AE.
Это более широкое ограничение, чем отсутствие визуальной картинки.

## Три разных режима

| Режим | Что исполняет работу | Нужен AE | Нужна CEP-панель |
| --- | --- | --- | --- |
| Offline AEP | Python/py-aep изменяет сохранённый файл | Нет | Нет |
| Live AE | ExtendScript через CEP либо иной dispatcher | Да | Зависит от transport; сейчас у нас да |
| Native render/validation | Движок AE, например aerender | Да, движок и зависимости | Для aerender не нужна |

[Adobe aerender](https://helpx.adobe.com/after-effects/desktop/render-and-export/automate-rendering/automated-rendering-network-rendering.html)
позволяет автоматизировать рендер из командной строки и по умолчанию запускает
новый экземпляр AE. Это вариант последующей проверки без управления панелью,
но не работа без AE. Наличие кадров не означает проведённую визуальную приёмку.

## Предлагаемое место в архитектуре

1. Продукт (Titles/Slideshow/пакетная подготовка): задание, шаблон, правила,
   выбор явно доступного способа исполнения и критерии результата.
2. Пакет типизированных операций `aep-file` (условное имя): inspect, build,
   ограниченные изменения и структурная проверка файлового артефакта.
3. Core: общий допуск, очередь/учёт операций и результатов; независимая проверка
   доступности offline backend и live AE. Python worker за узкой внутренней
   границей исполняет допущенный план через зафиксированную версию py-aep.
4. Панель: необязательный интерфейс статуса/просмотра/передачи результата в AE.
   Она не содержит Python-движок и не должна быть условием offline-вызова.

Это новый backend исполнения с файловым ресурсом, а не ещё один способ доставить
JSX в работающий AE. Его нельзя незаметно подставлять вместо live-вызова при
сбое CEP: состояние файла и несохранённое состояние редактора могут различаться.
Продуктовый компилятор может иметь два профиля операций; одинаковое пользовательское
намерение не обещает одинаковую поддержку и результат во всех backend.
Готовая папка module или общий MCP сами по себе не дают такого исполнения.

Адресный source review подтвердил текущую границу:
`core4/runtime/stdio-entry.js:31` фиксирует профили/модули/JSX assets, а строка240
связывает inspection availability с CEP peer. `core4/worker.js:19` и
`core4/core/artifacts.js:133` не дают обычному модулю произвольно запускать Python.
`core4/protocol/target-contract.json:35` и `core4/core/resources.js:64` используют
live identity/session и host origin. Следовательно, нужны отдельно допущенные
backend и файловая policy/schema, а не обход этих ограничений. На первом этапе
достаточно одного фиксированного offline-профиля; универсальный router всех
backend не является условием начала. Live inspection/mutation остаются
недоступными при отсутствии AE, даже если offline capability готова.

Не нужны второй публичный MCP/broker или публичный произвольный Python eval.
Python — дополнительная зависимость выбранного пакета, не обязательное условие
старта минимального Core. Детали установки окружения и подключения к Core
проектируются отдельным этапом; здесь они не объявляются готовыми.

## Файл, результат и передача в AE

Начальный вариант — только чтение исходника и создание новой копии:

`зафиксированный input → план/preview → новый candidate AEP → структурный отчёт → отдельная native/visual проверка`.

Источник — конкретный снимок сохранённых bytes с hash и версией формата.
Нужен проверяемый способ получить стабильный снимок, а не только сравнение path.
Несохранённые изменения AE в него не входят. Начальный scope не перезаписывает
исходник и не заменяет файл, который может оставаться открытым в AE.
Достаточно работать с независимым снимком; отсутствие AE не угадывается по path.

Worker пишет во временный файл своей операции, повторно читает его и проверяет
заявленный diff; публикация нового output имеет явный commit без перезаписи
существующего результата. После сбоя сверяются журнал и точный output, вместо
слепого повторного применения плана. Общие/пересекающиеся ресурсы сохраняют
ограничения; old live UNKNOWN не очищается запуском offline-задачи.

В отчёте отдельно сохраняются: input/output hashes, версия библиотеки/контракта,
список изменений/ограничений, structural check, native check и visual check.
Последние две проверки первоначально имеют статус «не выполнено».
При открытии candidate в AE начинается новый live этап с новой инспекцией цели;
hash файла и offline refs не являются adoption или разрешением изменения live.
Проверка относится к точному артефакту и окружению AE/шрифтов/плагинов/медиа;
последующее сохранение изменённого AEP создаёт новую версию артефакта.

## Польза и цена

Offline подготовка не требует старта AE, CEP handshake, controller открытого
проекта или удержания пользовательской сессии. Можно готовить варианты проектов
и разбирать сохранённые файлы на машине без AE. В этом сценарии независимость
от панели приносит прямую пользу, а не только удобство другого интерфейса.
Live-канал при этом может остаться CEP: offline модуль не требует его замены.

Экономия времени/RAM вероятна при массовой подготовке без запуска AE, но здесь
не измерялась. Затраты смещаются на поддержку формата, пакетирование Python,
проверку конкретных операций и последующую native приёмку. Поддержка local models
определяется MCP host/tool calling, а не наличием панели. Media/fonts/preferences
могут понадобиться конкретным операциям и должны быть явными зависимостями.

## Предлагаемый порядок без расширения текущего B1

- Сейчас зафиксировать разделение offline/live; B1 диагностики не расширять.
- После выбора этого этапа подтвердить локальную версию и ограниченный профиль:
  сначала inventory, затем одна простая операция в новую копию, например
  переименование композиции. Не начинать с полной типографики/expressions.
- Один целевой round-trip: исходник неизменён, изменилось заявленное поле,
  candidate повторно читается, затем отдельно открывается/проверяется в AE.
  Это проверка выбранного профиля, не весь каталог возможностей py-aep.
- После подтверждения профиля включить worker через явную offline capability
  Core, затем разрешать продуктам использовать её. Рендер/визуальная приёмка —
  следующий отдельный профиль, а не обязательное условие каждой файловой инспекции.

## Validation

Только чтение локальных исходников/документов и публичных первичных источников.
Bounded read-only scout выполнил поиск; отдельный architect проверил границы
текущей composition/worker/resource без правок и расширения scope.
Пакет не установлен/не импортирован; AEP не разбирались и не записывались.
Tests/live AE/MCP/CEP/install/Argon sends0. Документальная проверка — локальные
ссылки и git diff --check. Рекомендация не подтверждает local install или
совместимость py-aep с пользовательскими проектами.
