# Использование готовых решений и измерение расхода

Обновлено 12 сентября 2026 года. Исходное состояние и выборка обращений описаны
в [аудите от 11 сентября](ae-agent-reuse-audit-2026-09-11.md).

База теперь доступна внешнему Codex через MCP. Она содержит 181 reviewed
решение; четыре рецепта распределения ключей получили локальный генератор
плана. Генератор вычисляет последовательности ключей в JavaScript без второго
LLM-вызова. Остальные рецепты остаются инструкциями для составления typed plan.

## Рабочий маршрут

| Инструмент | Назначение | Объём ответа |
|---|---|---|
| `search_solutions` | Поиск по короткой RU/EN задаче | По умолчанию 3 результата, максимум 8 |
| `get_solution` | Реальный текст рецепта, ограничения, входы, builder contract | Текст страницами по 6000 символов; `nextOffset` для продолжения |
| `build_solution_plan` | Вычисление готового плана из полной инспекции | До 5 свойств, до 80 ключей на свойство |
| `propose_ai_agent_plan` | Серверный proposal из готового плана | Preview и action ID; confirmation token модели не выдаётся |

Пример поиска: `search_solutions({"query":"Равномерно распределить выделенные
ключи по рабочей области"})`. Затем передать найденный ID в `get_solution`.
Аргумент `toolNames` у `get_solution` позволяет получить полные схемы максимум
четырёх preferred tools, когда они нужны. Весь registry загружать не требуется.
Страницы продолжения не повторяют полные метаданные и builder contract.

Результаты поиска, чтения и построения плана не меняют AE и не вызывают
провайдера. Их аргументы и ответы всё равно входят в контекст внешнего Codex:
отсутствие второго LLM не означает нулевой расход токенов первого.

Для проверки готового плана использовать `propose_ai_agent_plan`, затем
`run_ai_agent_plan({"actionId":"…","dryRun":true})`. **MCP-маршрут нового
runner допускает только dry-run.** Реальное выполнение остаётся в существующем
CEP-процессе подтверждения: тот же план проходит backend proposal, preview,
confirmation и protected run. Самостоятельная передача моделью `confirm:true`
через MCP не заменяет этот процесс. CEP HTTP/API-контракты не изменены.

Порядок выбора закреплён в MCP initialize instructions, проектном `AGENTS.md`
и установленном навыке `ae-mcp-bridge-workflow`: найти решение, прочитать нужное,
получить недостающую свежую инспекцию, построить план, проверить результат.
Это повышает вероятность использования базы, но не гарантирует, что любая
модель будет следовать инструкции в каждой задаче. Это нужно проверять по трассам.

## Ограничения локального генератора

Поддерживаются следующие ID:

- `ar-distributekeyframesevenly-typed-plan` — между заданными границами;
- `ar-distributekeyframestoworkarea-typed-plan` — по рабочей области;
- `ar-distributekeyframestocomp-typed-plan` — по длительности композиции;
- `ar-distributekeyframestolayer-typed-plan` — по диапазону слоя.

Контракт и иллюстративный `example` возвращаются в `get_solution.planBuilder`.
Пример нельзя исполнять на текущем проекте: его индексы и ключи вымышлены.
Нужны реальные comp/layer identities, frame rate, границы, полный массив ключей,
`completeKeyframeCount`, упорядоченные индексы выбранных ключей и path из
инспекции. Каждый сегмент path содержит `propertyIndex`, `matchName` и
необязательное `name`; глубина ограничена пятью сегментами.

Допускаются только scalar values, отключённые expressions и linear in/out
interpolation у всех ключей. Bezier/hold/ease/spatial metadata, неполные массивы,
неизвестные поля, совпадения времён после округления к кадрам и повторные цели
отклоняются. Невыбранные ключи сохраняются. Mutation использует числовые пути
после проверки полного descriptor path, чтобы одноимённые свойства не подменяли
друг друга. Idempotency keys привязаны к конкретному запуску.

Builder формирует полную перезапись ключей и восстановление linear interpolation.
Runner перед первой записью сравнивает повторную инспекцию с исходными ключами;
после записи обязательно сверяет identity, property path, количество, времена,
значения и interpolation. Неизвестное/обрезанное evidence требует review,
расхождение завершает запуск с ошибкой. Границы рабочей области/слоя и frame rate
должны быть свежими и проверенными вызывающей стороной до построения плана;
локальный builder сам к AE не обращается.

Живое выполнение этих новых builders в пользовательском проекте в этом цикле
не проверялось. Проверены pure calculations, реальные backend contracts и runner
с фальшивой панелью. Это не визуальная приёмка в After Effects.

## Контекст внутреннего CEP-планировщика

Исправлено молчаливое отсечение user prompt на 20 000 символах. Планировщик
получает общий обязательный минимум, каталог релевантных инструментов, правила
нужных операций и ограниченный снимок проекта. Весь запрос ограничен 24 000
символами: если он не помещается, следует явный отказ до LLM-вызова.
Исходная задача ограничена 12 000 символами. Обязательные инструкции сохраняются
в конце provider payload; их наличие проверяет smoke.

Для общего chat transport длинный prompt сохраняется до 64 000 символов,
system — до 12 000; превышение лимитов отклоняется. История не теряет сообщения
молча: максимум 40 входных сообщений, совокупно до 256 000 символов. Внедрённый
system не вытесняет первое сообщение. Это символьные, а не токенные лимиты.

На контрольном запросе `Duplicate selected layers` со стрессовым снимком
из 500 слоёв собранный контекст содержит 13 397 символов; каталог — 2884,
подробно выбрано 12 из 119 MCP-инструментов. Исходный аудит фиксировал 31 339
символов даже без снимка с последующим отсечением до 20 000. Это разные
контрольные условия; числа показывают устранение переполнения, а не процент
снижения счёта Codex. Полный внешний MCP-каталог по-прежнему существует;
новый compact prompt относится к внутреннему CEP planner.

Инспекция ограничивается нужными целями; prompts и навык предлагают повторно
использовать ещё актуальные результаты. Общего кеша AE-индексов между мутациями
не добавлено: изменение проекта может сделать их неверными.

## Наблюдаемый расход

Запустить `npm.cmd run report:reuse`, при необходимости добавить
`-- --since 2026-09-12T00:00:00Z`. Отчёт читает локальные bridge/AI-журналы.
По умолчанию выбирается runtime port 3456; другой задаётся `AE_BRIDGE_PORT`.
`AE_BRIDGE_LOG_DIR` позволяет серверу и отчёту использовать отдельный журнал.
События старого формата без runtime metadata и серверы тестов на других портах
исключены. Отчёт не восстанавливает неизвестную историю задним числом.

Счётчики разделяют поиск, чтение рецепта, локальную сборку, planner hints,
заявленные `solutionIds`, выполненные планы, raw steps и размеры tool-ответов.
ID фильтруются по reviewed registry; декларация ID не доказывает причинную связь
между рецептом и успешным выполнением.

Usage внутреннего провайдера и repair-вызова сохраняется, когда провайдер его
вернул. Input/output/cached input учитываются отдельно; неизвестное остаётся
`null`. **Сервер не видит usage внешнего Codex App**, даже когда Codex использует
его MCP-инструменты. Значит, `report:reuse` показывает факт обращений к базе,
но не полный расход пользовательской задачи и не экономию в процентах.

## Набор для будущего A/B

Реальные сравнения ещё не запускались. Использовать отдельную восстановимую
тестовую сцену с одинаковым начальным состоянием для каждой попытки, одинаковые
модель/усилие/язык/AE version и несколько повторов. Варианты: `raw`, `typed`
без registry, `reuse` с поиском и builders. Доступные инструменты и условия
каждого варианта фиксировать отдельно; подсказка «не используй библиотеку» сама
по себе не доказывает чистый контрольный вариант.

| caseId | Задача | Проверка успеха |
|---|---|---|
| `inspect` | Показать активную композицию и выбранные слои | Верные identities, отсутствие изменений |
| `duplicate` | Создать по две копии выбранных слоёв | Число, имена, порядок и исходные слои |
| `camera` | Создать камеру с контроллером | Parenting, типы, параметры |
| `keys-even` | Равномерно разнести выбранные scalar linear ключи | Полные времена/значения, сохранность остальных |
| `keys-workarea` | Разнести ключи по рабочей области | Те же проверки плюс границы |
| `deep-precomp` | Независимо дублировать дерево precomp | Ссылки и отсутствие связи с исходными comp |
| `template-text` | Заменить текст в трёх заданных слоях | Текст, стиль и отсутствие посторонних изменений |
| `batch-label` | Изменить метки указанной группы слоёв | Только выбранные identities и нужный label |

Записывать usage внешнего Codex и всех дополнительных planner/repair-вызовов,
время и все неудачные попытки до конечного исхода задачи. Если usage недоступен,
ставить `null`, не рассчитывать его из символов.

Команда `npm.cmd run report:reuse-ab -- <путь-к-JSON>` агрегирует такой набор.
Одна запись массива — одна законченная задача, включая её retries. Поля:
`caseId`, `variant`, `repetition`, `model`, `effort`, `aeVersion`, `baselineId`,
`language`, `success`, `verified`, `durationMs`, `usage`. `baselineId` — версия
общего набора исходных сцен. `usage` равен `null` либо объекту с тремя обязательными
полями `inputTokens`, `outputTokens`, `cachedInputTokens` (числа или `null`).

Отчёт не смешивает настройки; `matchedTrialSets` показывает, совпадают ли
caseId/repetition у присутствующих вариантов. `costPerSuccessfulTask` — вектор
токенов на одну успешную проверенную задачу с учётом неудач, а не денежная цена.
При неполном usage или отсутствии успехов он равен `null`. Совпадение наборов
не гарантирует отсутствие экспериментальных ошибок или одинаковый cache state.

## Проверки

`smoke:solutions` включает 12 пар RU/EN запросов, 6 дополнительных русских
перефразировок, попадание всех 181 точных названий, read-only и no-match cases,
арифметику/отказы builders, exact verifier, telemetry и A/B-агрегатор.
Исходные 12 RU запросов не находили решений; теперь ожидаемые решения
присутствуют в top-3. Эти примеры не доказывают качество произвольного русского
запроса: поиск остаётся словарным, без семантического LLM/embedding-вызова.

`smoke:bridge` проверяет stdio MCP discovery/proposal/dry-run, изолированный
runner и неизменность существующих gates. Provider/API smokes используют
заглушки. После обновления daemon поиск, builder и явный dry-run доступны
также старым MCP adapters. Новые клиенты получают уточнённые instructions
при initialize; прямое реальное выполнение остаётся закрытым.
