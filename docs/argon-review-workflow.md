# Ручное ревью этапов через Argon

Единица правила — один самостоятельный scope/этап: одно review для него и
локальное применение замечаний. Первое review нового самостоятельного этапа
может быть покрыто действующим общим поручением пользователя; повторно просить
согласие только из-за перехода к такому этапу не требуется. Новое явное поручение
нужно для дополнительного review уже рассмотренного среза, а не для каждого
первого review внутри ранее авторизованной работы.

Документальный workflow для одного ограниченного Argon review по явному поручению пользователя. Для него выбирается подходящий предмет и момент: например, план до реализации или конкретный зафиксированный результат. Автоматическая пара «план → результат», обязательный повтор после исправлений и итоговый review как условие выпуска не предусмотрены. Argon review не добавляет runtime authority, автоматических hooks, обязательного внешнего вызова при каждом старте или платного API. Малые правки не требуют искусственного review. [Основной план](../plans/core-4.0.0.md).

Оно не создаёт автоматических повторных review: дополнительное обращение к Argon по тому же срезу требует нового явного поручения пользователя, даже если Argon попросил перепроверку. Ни review, ни это поручение не расширяют AE authority, save/destructive/raw gates, доступ к секретам, платным API, публикации или аккаунтам.

| Возможный предмет одного review | Когда его уместно выбрать | Что делает владелец задачи после ответа |
| --- | --- | --- |
| План или архитектурное решение | До реализации, если именно контракт или план составляет основной риск | Разобрать findings на snapshot и зафиксировать локальное решение; выполнить релевантные технические проверки |
| Конкретный завершённый результат | После существенного межкомпонентного изменения, если для этого этапа ценнее проверка реализации | Разобрать findings на точном commit/diff, подтвердить их адресными evidence, исправлениями в разрешённом scope и локальными проверками |

Выбирается только один предмет из подходящих для данного поручения; второй тип review не запускается автоматически. После ответа root самостоятельно решает статус каждого замечания и подтверждает вывод локальными evidence и релевантными техническими проверками в разрешённом scope. Исправление boundary, просьба Argon о повторе и готовность к выпуску не создают новый review gate. Новый запрос возможен только по новому явному поручению пользователя. При недоступном Argon продолжается независимая безопасная работа; техническая приёмка всё равно требует собственных evidence. Максимальное усилие подтверждается доступными элементами UI; просьба в prompt не доказывает выбранную настройку. Если отдельного effort control нет, контроллер фиксирует этот предел, не выдумывая его наличие.

## Основной режим: проверка замечания внутри согласованного исправления

После ответа выполняется локальный разбор на доступном evidence без обязательного повторного обращения к Argon. Статус «требует проверки» допустим; владелец задачи выбирает достаточную адресную проверку в разрешённом scope. По подтверждённому замечанию — минимальное исправление и релевантная локальная регрессионная/техническая проверка. До подтверждения замечания исправление вслепую не внедрять.

Если замечание не подтверждается, устарело или уже исправлено, отдельно записать расхождение с ответом Argon: snapshot, доказательство, актуальный статус и влияние на scope; необоснованную правку не делать. Расследование и изменения за пределами авторизованного scope не выполнять. Уже выполненные проверки переиспользовать при той же версии/source closure и условиях, с исходным логом/командой/результатом; повторять локальную проверку при изменении кода/условий, новом сбое либо неразрешённом риске. Совпадение SHA одного файла не доказывает неизменность всей closure. Новый Argon review не возникает автоматически даже при изменении boundary или неразрешённом риске: он требует нового явного поручения пользователя. Обязательного Argon review перед объявлением выпуска нет.

## Сохраняемый пакет

Каталог `reviews/argon/<stage-id>/<review-id>/`; review-id уникален, например `20261026-m2b-result-01`. Файлы отправки и локальные записи разделены явной allowlist в manifest; не отправлять весь каталог автоматически.

| Файл | Обязательные данные и назначение |
| --- | --- |
| `request.md` | Тип `plan/result`, review/stage IDs, цель, вопросы, snapshot, границы, требуемый формат ответа |
| `manifest.json` | Статус `DRAFT/INCOMPLETE/COMPLETE`, review/stage IDs, полный base/target commit, plan digest для plan-review, dirty status, список payload-файлов с ролью, размером и SHA-256, исключения/redactions, ограничения; `externalAllowlist` и получатель |
| `context/` | Только необходимые allowlisted выдержки/документы/исходники; каждому фрагменту — commit, path, исходные строки и SHA-256 полного файла |
| `changes.diff` | Для result: точный diff `base..target`, команда получения, список файлов, отсутствие обрезки; исключённые бинарные данные перечислены |
| `evidence/` | Команды, среда, время, exit code, результаты и хеши логов; tested commit или точная source closure. Старый PASS явно исторический |
| `approval.json`, `submission.json` | Локальные записи: разрешённые request/payload/manifest SHA-256, пользовательское согласие и время; фактический получатель, попытка, состояние отправки, ссылки/receipt. В пакет не входят автоматически |
| `response.txt`, `response-meta.json` | Неизменённый ответ и метаданные: SHA-256, receipt, request digest, reviewed commit/plan digest, полнота/обрезка, указанный verdict; неизвестные поля остаются `null` |
| `decisions.md` | Разбор Codex, статусы, evidence, известные задачи и согласованные дальнейшие действия |
| `verification.md` | Проверки пакета, пробелы и итог: готовность к передаче отдельно от внешнего verdict и принятия результата |

Manifest не включает собственный хеш: его digest фиксируется в approval/submission. Хеши response и decisions пишутся в локальную часть manifest после получения; при этом сохраняется неизменённый manifest отправки и его digest. Любая новая версия отправляемого payload получает новый review-id. Полный SHA важнее имени ветки; зафиксировать clean snapshot перед result-review. Незакоммиченные изменения после snapshot исключить и явно показать. Для плана фиксировать base commit и digest конкретной редакции плана, не обещать будущий код.

`COMPLETE` означает лишь проверенную комплектность локального пакета. Неизвестный исход отправки или отсутствующее evidence не превращаются в `PASS`. Пропуски/неподобранные файлы/обрезка/непринятые redactions сохраняют `INCOMPLETE`, пока пользователь явно не примет перечисленную неполноту; это принятие не является разрешением отправки.

## Ответ Argon и разбор Codex

Запрашивать: review/stage IDs, тип review, полный reviewed commit (и plan digest), request SHA-256, перечень прочитанного/пропущенного, verdict `go/revise/stop/insufficient-evidence`. Для каждого finding: стабильный ID, приоритет P0–P3, утверждение, сценарий отказа, конкретные `path:line`/test evidence, уверенность и минимальная рекомендуемая проверка. Отдельно: известные ограничения, гипотезы, упрощения и отсутствующее live evidence. Если модель не может подтвердить binding/полноту, пусть прямо это укажет.

Codex разбивает составные findings на отдельные проверяемые утверждения; рекомендации тестов/упрощений связывает с ними, не теряя отдельные новые пункты. Для каждого записывает:

- **Подтверждён:** воспроизведение либо достаточное адресное доказательство на target snapshot; команда/exit/test/log или точный source argument. Дефект ещё не исправлен.
- **Уже учтён:** ссылка на существующую задачу/ограничение либо исправление с commit и проверкой. Уточнить `known-open` или `fixed-verified`; учёт не равен исправлению.
- **Не подтверждается:** конкретное противоречащее evidence и границы вывода. Отсутствие воспроизведения само по себе недостаточно.
- **Требует проверки:** чего не хватает, какой bounded test/source review нужен и кто может разрешить его. Пробел нельзя закрыть догадкой.

Обязательные столбцы: finding ID, внешний и локальный приоритет (с причиной изменения), статус, evidence `commit:path:line`/test ID/лог, новизна `new/known/duplicate/unknown` и ссылка на известную задачу, следующий безопасный шаг. Если список известных задач недоступен, писать `unknown`, не заявлять новизну. Сравнивать с известными планами/issue IDs; другие активные чаты не трогать без отдельного поручения.

Нельзя переносить ответ на новый commit по одному совпавшему имени файла или зелёным старым тестам. Сверить diff и актуальные зависимости; изменённые строки и evidence closure требуют новой проверки. Совпавшие bytes — только provenance, не независимое доказательство корректности. Несовпадение request/commit/plan binding помечается `historical/unbound`; результат не принимается как review текущего этапа.

## Сбой и неизвестный исход

Состояния: `prepared` → `approved` → `submitted` → `received` → `triaged`; отдельные `blocked`, `submission-unknown`, `historical-only`. При сбое сохранить действие, цель, время, попытку, receipt/лог, точную причину, `denied/pending/uncertain` и выполненную часть. Этап остаётся **не проверен Argon** до корректно привязанного ответа. Сначала выяснить предыдущий исход через существующий контроллер; неизвестный исход не повторять. При отказе не обходить его. Любая повторная попытка отправки требует нового явного поручения пользователя, существенно новых релевантных данных, подтверждения, что предыдущее действие не выполнено, и собственного receipt. Никаких повторов вслепую, бесконечных повторов или смены канала/модели ради обхода.
