# Политика рутинной диспетчеризации AE Agent

Обязательный контракт распределения самостоятельных блоков работы. Это правила
принятия решений диспетчером, а не программный планировщик или автоперехватчик.

## 1. Классификация блоков диспетчером

Перед началом самостоятельного блока и после закрытия сложного инженерного
блокера диспетчер классифицирует задачу:

- **Luna (`ae_scout` / `ae_operator`, high):** простой анализ нескольких файлов,
  сведение evidence, разбор logs/report и правка по понятному образцу.
- **Sol 6.1 / high (`ae_implementer`):** scoped реализация, отладка и содержательная
  техническая валидация. XHigh (`ae_specialist`) — сложные взаимодействия компонентов,
  safety/security/authority и устойчивые дефекты.
- **Sol 6.1 / xhigh (`ae_architect`):** обычная архитектура, системные границы и сложное планирование.
- **Sol 6.1 / ultra (`ae_architect_ultra`):** особо сложные архитектурные решения
  или содержательная эскалация после XHigh; обязательной лестницы для каждой задачи нет.
- **Sol 6.1 / high (`ae_reviewer`):** независимое ограниченное review по необходимости.
- **Flash 3.8 / configured High (`ae-agent`):** ограниченные правки с ясной приёмкой
  в категориях с уже подтверждённой пользой, без повторного разрешения в AE Agent.
- **Диспетчер сам:** координация, решения о scope, единоличное управление AE/CEP/UI,
  а также один готовый короткий вызов проверки. Сложные блоки распределяются по
  существующей таблице `docs/model-routing.md`, а не автоматически остаются у родителя.
  Серия готовых вызовов или чтений не является льготой для выполнения диспетчером.
- **Скрипт без LLM:** предсказуемый цикл ожидания и парсинга выполняется одним
  запуском существующего скрипта с выводом compact summary.

## 2. Исключения к маршруту по scope

Делегирование рутины обязательно, кроме конкретных исчерпывающих случаев:

1. Прямое указание пользователя (human executor override).
2. Заняты оба доступных слота исполнителей.
3. Нет безопасной независимой части или требуется прямой sole AE controller.
4. Доказанная недоступность исполнителя после сверки статуса и процесса.

При отказе фиксируется короткая причина; при освобождении ресурса выбор пересматривается.
Недоступность AGY по доступу не требует вызова Astra. Выбранная пользователем
модель чата не запрещает делегировать и не может изменяться автоматически.

## 3. Контекст и изоляция поручений

- Для ограниченных ролей Codex (Luna/Sol) передаётся `fork_turns: none`. Для Flash
  формируется автономный task packet (поле fork не используется).
- Передаются: исходная цель, точные пути релевантных файлов, baseline, границы
  ownership и критерии приёмки. Весь чат целиком по умолчанию не передаётся.
- Исполнитель возвращает компактный ответ по схеме без избыточного эха.

## 4. Защита мутаций и границы проектов

- Перед любой мутацией обязательны свежие guards и неизменные AE gates.
- Строгий лимит: один sole controller и максимум два помощника, включая AGY.
- В других проектах Flash допускается только по профильной политике или прямому
  поручению; глобальный AE grant отсутствует.

## 5. Формат фиксации решений и валидация

Диспетчер кратко фиксирует выбор в обычном progress или существующей заметке этапа,
без аудита каждого чтения:

`[block: <имя>] [executor: <роль/модель>] [reason: <причина>] [ownership: <файлы>]`
Валидация опирается на фактические metadata и артефакты; правка config не доказывает runtime.

## 6. Примеры маршрутизации

1. **Извлечение JSON долгого прогона и логов:** -> `ae_scout` (Luna/high).
2. **Точечная правка шаблона документа по образцу:** -> `ae_operator` (Luna/high).
3. **Реализация обособленного хелпера по ТЗ:** -> `ae_implementer` (Sol/high).
4. **Запуск одного npm-валидатора:** -> диспетчер сам.
5. **Серия проверок:** содержательная техническая валидация -> Sol/high; простая
   сводка готовых результатов -> Luna, предсказуемый запуск/парсинг -> существующий скрипт.
6. **Неопределённый исход операции AE:** -> сверка sole controller без повторного запуска.
7. **Ограниченная правка в подтверждённой категории:** -> Flash configured High.

Неудача Flash допускает Sol/high в прежнем scope после сверки процесса и эффектов.
При ясном safety/authority или системном вопросе не ждать двух неудачных исправлений.
Нерешённая инженерная сложность Sol/high -> `ae_specialist` (XHigh); обычная
архитектура -> `ae_architect` (XHigh); особо сложная архитектура или содержательная
эскалация после XHigh -> `ae_architect_ultra` (Ultra). Astra — только после
содержательной неудачи Ultra с записанными попытками, включая XHigh, если была,
проверенными гипотезами и оставшимся пробелом. Ошибки доступа диагностируются отдельно.

## 7. Ограничения автоматизации

Настоящие правила направляют выбор модели диспетчером, но сами не перехватывают
вызовы API/инструментов (`spawn_agent`) и не дают технической гарантии автоматического
назначения. Успешный единичный smoke не доказывает поведение всех будущих диалогов.
