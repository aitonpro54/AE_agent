# Панель AE и переносимость между AI-клиентами

1 ноября 2026. Дополнение к [исследованию MCP](mcp-base-comparison-20261101.md)
по прямому вопросу пользователя. Документальный research; смена transport,
установка сторонних продуктов и новые live действия не выполнялись.
Под «Cloud Code» в сравнении подразумевается Claude Code; для облачного агента
отдельно указана граница удалённого доступа.

## Вывод

Дополнение: [работа с закрытыми AEP через py-aep](offline-aep-module-research-20261101.md)
— самостоятельный offline backend без AE, а не замена CEP transport для live AE.
Он усиливает требование необязательности панели для файловых операций, но не
требует удаления панели из live-канала.

Наличие панели и выбор AI-клиента — независимые архитектурные решения.
MCP-интерфейс позволяет подключать разных клиентов как к CEP transport,
так и к файловому transport. Отказ от панели сам по себе не переносит
установщик, инструкции, модельные возможности или гарантии исполнения.
Целесообразная граница: продукты/операции и Core не зависят от клиента;
регистрация клиента и доставка команды в AE имеют отдельные адаптеры.
Необязательная панель — возможная цель, ещё не свойство нашей поставки.

## Что переносится

| Часть | Что меняется при смене клиента | Зависимость от панели |
| --- | --- | --- |
| Задания, схемы, deterministic compiler продукта | Предпочтительно ничего; проверяется совместимость контрактов | Не нужна для вычисления плана |
| Core, очередь, журнал, ограничения исполнения | Общий runtime сохраняется; новый клиент получает собственное подключение и controller lease | Замена CEP не требуется ради нового клиента |
| MCP-регистрация и работа агента | Формат config, launcher, permissions, инструкции, timeout/reconnect и tool calling | Не решаются удалением панели |
| Исполнение в AE | CEP evalScript либо другой подтверждённый механизм dispatch/result | Здесь панель сейчас обязательная часть канала |

Локальное evidence: `core4/tools/install-core4.js` пишет
`[mcp_servers.after-effects-core4]`, defaults указывают `.codex/config.toml`.
Следовательно, универсальный installer для других клиентов ещё не доказан.
`products/titles/src/compiler.js` использует Node, schema и module contract;
`products/titles/WORKFLOW.md` отделяет compile/prepare-build от Core controller.
Это пригодная основа переноса, но фактического запуска в других клиентах нет.
`docs/portability.md` сейчас принимает round-trip Windows/AE/CEP/Node/Codex,
а не совместимость всех AI-клиентов. Этот research не расширяет её PASS.

[Antigravity](https://antigravity.google/docs/mcp) документирует command/args/env
для stdio и конфигурацию собственных MCP-серверов;
[Claude Code](https://code.claude.com/docs/en/mcp) — локальные stdio-серверы;
[LM Studio](https://lmstudio.ai/docs/app/mcp) — локальные и удалённые MCP для моделей.
Поддержка протокола у клиента не доказывает совместимость нашей точной версии:
требуется ограниченная проверка handshake, discovery, результата/ошибки и lifetime.
Повторять всю продуктовую приёмку только ради нового config необязательно;
меняющиеся зависимости и поведение клиента определяют релевантный scope.

Локальная модель требует host/agent loop, вызывающий инструменты и возвращающий
их результаты модели. Нужны достаточные tool calling, контекст и выполнение
многошаговой инструкции. Компактные контракты, выбор доступных операций и
детерминированные builders влияют на стоимость сильнее самого вида AE transport.
Умение модели писать код и умение надёжно выполнять продуктовый workflow —
разные критерии. Инструкции и вспомогательные shell/browser tools не переносятся
автоматически вместе с MCP. Если агент работает в облаке, локальный stdio
на компьютере с AE ему недоступен без отдельного разрешённого соединения;
наличие или отсутствие панели этого не меняет.

## Что даёт наша панель и почему она появилась

Зафиксированный installable-план выбрал внешний Node, аутентифицированный
CEP peer и reviewed JSX без C++ SDK. CEP предоставляет штатный вызов
`evalScript` с callback в scripting engine host: это описано в
[Adobe CEP Cookbook](https://github.com/Adobe-CEP/CEP-Resources/blob/master/CEP_12.x/Documentation/CEP%2012%20HTML%20Extension%20Cookbook.md).
Это техническое основание выбора. Полного исторического сравнения стоимости
CEP и всех беспанельных решений в прочитанных планах нет; нельзя утверждать,
что CEP когда-то доказанно победил их по эффективности.

В текущих `core4/cep/index.html` и `core4/cep/js/panel.js` видимая часть —
кнопка подключения, состояние и пояснение ошибки. Чата, редактора шаблонов
или пользовательского интерфейса Titles там сейчас нет.
Исполняющая часть аутентифицирует канал, получает команды через long poll,
передаёт их фиксированному dispatcher/evalScript и возвращает completion.
Там также есть recovery/latch проверки. Закрытие панели уничтожает этот endpoint;
выкинуть HTML без замены канала нельзя. Основной owner/журнал остаётся вне CEP.
Окно native confirmation не тождественно HTML-панели: его сохранение возможно
при другом dispatch, но требует соответствующей технической проверки.

Наличие панели не доказывает исход команды, точную смену проекта или отмену
после разрыва соединения. Скрыть окно и отказаться от CEP — также разные вещи.
Cookbook описывает invisible extensions, но AE отсутствует в приведённой таблице
поддерживающих их приложений. Это недостаточно для обещания простого фонового
CEP в нашей версии AE; отсутствие в таблице не доказывает невозможность.

## Рыночные примеры

| Решение | Роль панели | Связь с внешним AI |
| --- | --- | --- |
| Atom (предположительно упомянутый пользователем «Atoma») | Чат внутри AE; в MCP-режиме панель остаётся обязательным мостом | Документированы Claude Code, Codex CLI, Cursor и локальный MCP URL |
| OnePrism | Статус, диагностика, настройки доступа агента; отдельная вкладка ручных AI-инструментов | Внешний клиент соединяется с hosted MCP; панель должна быть открыта и авторизована |
| Adobe AI Assistant beta | Встроенный dockable Assistant с запросами и результатами | Рассмотрен как пример UI, не как доказанный внешний MCP или готовая замена Core |
| Kumo / 23d1 | CEP-панель для основного пути не нужна | Внешний MCP → dispatch JSX и файловые результаты; различия recovery разобраны в исходном research |

Это особенно наглядный контрпример предположению «панель привязывает модель».
Преобладание панелей во всём рынке не установлено этой небольшой выборкой.
Вывод о коммерческой ценности UI — наша интерпретация функций: работа из AE,
понятное подключение, настройки и поддержка, а не доказательство превосходства
транспорта или внутренних гарантий закрытых продуктов.

## Стоимость и рекомендация

При смене AI-клиента наиболее прямой путь — сохранить Core/операции/AE bridge
и адаптировать клиентское подключение. Для беспанельной эксплуатации выигрыш
может дать отсутствие установки/открытия CEP и его Chromium-окружения;
затраты переходят в dispatcher, файлы результатов, идентификацию AE и recovery.
Размер RAM, задержки, трудозатраты и расход токенов не измерялись. При одинаковых
tools/results нижележащий transport сам по себе не уменьшает контекст модели.
Беспанельное подключение не означает работу без AE или его графической сессии.

Рекомендация: сохранять независимость Core и модулей от AI-клиента и панели;
не считать поддержку двух AE transports бесплатной. Если сравнение transport
продолжится, сначала узкий read-only эксперимент и существующие сценарии
потери/позднего ответа; выбор одного основного transport до продуктового роста.
Опциональный UI не требует немедленно поддерживать два production transport.
B1-диагностика не превращается в одновременную миграцию всей архитектуры.
