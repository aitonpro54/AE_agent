# Автономный фотомонтаж в AE Agent Core

9 ноября 2026. Инженерный план по итогам аудита A1–A13 и повторного ревью Аргона с исходниками. Точка передачи — коммит аудита `4e24a9e`. Новый чат сверяет фактический HEAD, локальные изменения, установленные составы и доступность машин перед работой. Исторические PID, ID команд и хеши из отчёта нужны для анализа инцидента.

Результат — Core сам находит точные цели в открытом проекте, размещает подготовленные изображения поверх исходных слоёв с сохранением поддерживаемых свойств, проверяет изменения и отдаёт контрольные PNG. Обычная согласованная задача выполняется без Kumo, ручных кликов в AE и удалённого рабочего стола. После сбоя Core показывает исход операции или причину, по которой исход пока нельзя установить. Проверка проходит на рабочих копиях. Выпуск видео через R1 относится к отдельному плану.

### Переиспользование кода

Перед реализацией каждого затронутого блока сверить текущие модули Core и собственные прежние наработки. Сначала взять подходящие реализации, контракты и тесты Core. Затем проверить legacy AE Agent, сохранённый в `mcp-server`, на нужные предметные операции и пограничные случаи. Kumo рассматривать там, где остаётся конкретный пробел или его вариант лучше подходит по проверяемым свойствам.

| Задача | Что проверить в нашем коде |
|---|---|
| P0a/P1b, контекст и зависимости | Legacy `find_project_items` с ID-фильтром, `get_comp_details`, `get_layer_details` и `get_placeholder_usage` как источники полей и проверок. Актуальные выбор цели, ревизия и бюджет чтения остаются за Core. | P1a, дублирование и замена | В legacy `duplicate_layer` есть нативное дублирование, снимки оригинала и копии и проверка числа слоёв. Сопоставить эти части перед написанием нового исполнителя. Из legacy переносить нативные операции и проверенные идеи. Идентичность цели, права, допуск, квитанции и восстановление определяет Core. Для нового контракта обязательны точные ID и ревизия. Старый выбор по индексу или имени и включённый по умолчанию `fixExpressions` в контракт не переходят. Из Kumo основной кандидат P0a — диагностика модальных окон Windows. При переносе кода закрепить исходник и MIT-атрибуцию. В Decision Log блока отметить, что взято из Core, legacy или Kumo, и какую проверку это сохраняет.

### Инварианты для реализации и проверки

- `delivered` фиксирует handoff. Начало native исполнения подтверждается отдельно. Для позднего результата чтения нужны ограниченное окно ожидания, заблокированная выдача новых команд, проверка исходных epoch, peer, command, binding и pins, запись terminal receipt и понятный статус вызывающему клиенту. Проверить отсутствие poll, потерянный HTTP-ответ после handoff, просроченный dry-run, reload панели, потерю привязки, callback после дедлайна и истечение окна. Сохранить UNKNOWN при неоднозначности. Исторический `native-read-disposition` остаётся валидатором своего случая.
- Диагностика Windows может сообщить наблюдаемое модальное окно и результат проверки. Heartbeat и отсутствие lock не доказывают эксклюзивность. Синхронный JSX и Undo group не дают обещания отката всех эффектов. При переиспользовании MIT-кода закрепить источник и лицензию. Kumo остаётся отдельным инструментом для изолированных процессов и копий. Импорт результатов между копиями требует проверки зависимостей и владения.
- Проверить старые layer ID, source ID и относительный порядок. Для нового слоя проверить ID, source, placement, тайминг, transforms и ключи, masks/effects, parent, matte и alpha в объявленном профиле. Проверить cross-comp ссылки, `LAYER_INDEX` и enabled expressions в области влияния. При неполной доказуемости отклонять запись до мутации. Измерять корректность на структурных проверках и выбранных кадрах. PNG дополняет проверку зависимостей.
- Для больших проектов проверить границы 255/256/257, 499/500/501, 511/512/513 и 1079+. Измерить итоговые UTF-8 байты с экранированием, дублированием snapshot/revision/receipts и всеми потолками транспорта, схемы и восстановления. Сохранить защищаемые поля инвентаря и `checkBytes` после confirm. Потоковое хеширование и копирование проверять вместе с file identity, stamps и checkpoint. Новые лимиты выбирать по результатам измерений. Для open с неизвестным заранее состоянием явно проверять последствия после вызова.
- Отдельно вести результаты исходников, стенда, установленного MCP/CEP на каждой машине и рабочего обновления. Проверки привязывать к актуальному составу. Применять существующие installer и module admission. Переиспользовать доказательства неизменённых частей, запускать регрессии затронутых контрактов и smoke совместимости Titles, Slideshow, import, insert и PNG. Сохранять локальные credentials, state, preferences и соседний config.
- В сквозном прогоне раздельно записать ожидание пользователя, подготовку файлов, AE dispatch, восстановление и визуальную проверку. Если генерация и reasoning измеряются, вести их отдельными стадиями. Сравнить число вмешательств, restart после чтения, повторы импорта и дубликаты. Указать размер выборки и покрытие данных. p50/p95 приводить при достаточном числе повторов, wall time подписывать как время вызова. Токены запрашивать по правилам Codeburn, где есть подтверждённое покрытие. Причина прежнего сбоя удалённого доступа остаётся открытой без журналов этого сеанса.

#### P1b, файловый профиль сохранения

- **Progress.** Потоковый SHA-256 и эксклюзивная копия checkpoint подключены к save и lifecycle/open. Контракты среза допускают до 96 МиБ. Координатор выполнил самостоятельный файловый блок параллельно двум занятым слотам P0, затем проверил его через существующий TEMP-стенд.
- **Decision Log.** Переиспользованы `plainPath`, проверка file identity, stamps, SHA и fsync из текущих Core save/lifecycle, а размер блока 1 МиБ взят из `media-layer-proof`. Полная побайтная проверка `checkBytes` после confirm сохранена. Копия повторно читает исходник и сверяет ожидаемые bytes/SHA до принятия checkpoint. Предел 96 МиБ покрывает измеренный размер 95724372 байта с запасом около 4,7 МиБ. Это кандидат для нативной проверки save/open. Inventory и ограничения транспорта относятся к отдельному блоку.
- **Validation.** На DESKTOP-32974QF один файловый прогон синтетических 95724372 байт дал 190 мс на SHA, 319 мс на копирование с fsync, 189 мс на проверку SHA копии. `project-save` и `project-lifecycle` дали 15/15 PASS, включая существующий checkpoint, несовпадение stamp, предел 96 МиБ + 1 и drift после confirm. Синтетические данные проверяют файловый путь, live save/reopen валидного AEP такого размера открыт.
