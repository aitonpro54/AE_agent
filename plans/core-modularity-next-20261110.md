# Модульная поставка после R1 на MSI

## Цель и исходная точка

Пользователь поручил проверить архитектуру, проконсультироваться с Argon и
подготовить дальнейший план для нового чата. База `8e3b718db3c695190a45607064ac04e11d4d5558`,
ветка `codex/ae-agent-core-4.2.2`. Реализация начинается отдельным поручением в новом чате.

Цель — поставлять и обновлять операции независимо в пределах явно поддерживаемых
контрактов, собирать Core под объявленный сценарий и проверять только затронутые
границы. Разработка и нативная приёмка проходят на MSI. Последующий перенос на
десктоп использует принятую установку, preflight и read-back.

## Локальный порядок до завершения консультации

1. **M0. Контракт состояния при обслуживании.** Составить матрицу prepare intent,
   prepared, submitted/rendering, cancel pending, unknown, verified partial,
   publish intent, completed/cancelled. Проверить concurrent start и границу
   freeze → inspection → stop certificate → update → enable. Сначала адресные
   source/TEMP проверки. Определить условия отказа до изменения установки и
   обращения со старой историей. Продолжение после смены пакета требует явной
   совместимости state/toolchain, исходного ID и доказательства отсутствия replay.
2. **M1. Расширение отдельной поставки обычной операции.** Первый кандидат
   `comp-render/completion.json`. Сохранить exact public contract и отдельно
   закреплённый admission. Дополнительные data-only файлы перечислены в manifest,
   проходят hash/size/path проверки и существующий доверенный профиль. При
   обновлении одного слота проверить прежние hashes остальных операций/runtime,
   детерминизм сборки и сохранность истории. Старый формат capability поддерживается.
   Новый формат получает явную версию. Проверить downgrade, лишние файлы,
   отсутствующие зависимости, подмену admission и несовпадение схемы данных.
3. **M2. Декларация доверенного сервиса R1.** Использовать закрытый идентификатор
   известной возможности. Проверка декларации согласует package verification,
   MCP discovery, Owner dispatch и разрешение stage-render-copy. Порядок и
   конкретная схема подлежат уточнению после получения ответа Argon. Произвольные пути
   загрузки исполняемого кода из деклараций не допускаются.
   Отсутствие capability, неподдерживаемая версия и неполный набор файлов
   должны одинаково отклоняться клиентом, упаковщиком и Owner. Проверить
   коллизии имён методов и запрет обхода отсутствующего сервиса прямым вызовом.
4. **M3. Минимальные и совмещённые составы.** Собрать render-only сценарий для
   существующего сохранённого AEP и сохранить явный montage+render сценарий.
   Проверить необходимые inspection, project lifecycle, checkpoints,
   confirmation и file/process proof. Новый selector с теми же возможностями
   собирается без изменения bootstrap. Исторические release v1/v2 имеют
   проверяемый совместимый путь. Минимальный состав должен исключать функции,
   которые не нужны его сценарию, включая транзитивное наследование.
5. **M4. Штатная приёмка MSI.** После предыдущих проверок провести установку и
   обновление, fresh configured MCP read, один render на копии AEP и разбор
   судьбы задания при обслуживании. Сверить байты независимых модулей,
   installation identities, локальные настройки, историю и терминальные IDs.
   Отдельно зафиксировать границы поддерживаемого независимого обновления R1.

## Decision Log

Первоначальное предложение начинало с декларации R1. Локальный аудит ставит
контракт обслуживания первым. Малый пилот data-only файла позволяет проверить
расширение поставки на существующем типе операции до развития service lifecycle.
Число строк или каталогов не служит критерием завершения модульности.

Каждый этап должен давать работающий commit, адресные проверки и запись
Progress / Decision Log / Validation. Первое сообщение нового чата должно
содержать точный принятый порядок после triage Argon и актуальную точку входа.
