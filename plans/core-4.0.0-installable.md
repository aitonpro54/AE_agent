  тестовой копии AEP `cca3be6e…` совпал с исходным. After Effects 28804
  остался открытым.

### Decision Log

- `get_module_contract` показывает `operatorConfirmation` для включённых
  профилей. После сверки эффекта предложения локальный оператор вызывает
  `node <release>/runtime/operator-confirmation.js <installation.json> <packageHash> <proposalId> <operatorApprovalDigest> <sessionId>`.
  Сразу после выдачи допуска идут свежий `dry_run_plan` и `run_plan`.
  Допуск относится к одной операции и привязан к proposal, сессии, исходному
  снимку, checkpoint и reservation. Проверки сохранения, перехода AEP и
  очистки принадлежащих Core объектов продолжают действовать. Нативный
  реестр проверяет срок допуска перед вызовом и в точке прежнего окна.
- Вызов `RenderQueue.render()` перенесён из
  [исполнителя 3.3.5](../mcp-server/native-render-variant.js#L236). Core
  сверяет текущую ревизию проекта, ID и настройки временной копии, свободный
  путь и единственную включённую строку. По окончании требуются нативный
  `DONE`, исходная квитанция и читаемый файл. При неопределённом результате
  исходное задание и байты остаются доступны для сверки.
- Длинный мастер использует [`aerender-jobs`](#8-ноября-асинхронный-рендер-мастера-на-msi)
  на сохранённой копии с подготовленной очередью. У синхронного запуска
  остаётся предел `comp-render` в 600 кадров и 12 секунд таймлайна, а
  получение ответа зависит от времени рендера и тайм-аута CEP. При `UNKNOWN`
  применяются штатная сверка и запрет повтора.
- Открытые UI-сценарии и пробелы. Первое открытие и переоткрытие CEP после
  смены пакета, нативные предупреждения Adobe, ручное создание нового
  шаблона Slideshow S1 с перекрытием и ключами прозрачности. Существующий
  S1 использует подготовленный шаблон. Для снимка открытой композиции
  доступен старый `save_comp_frame_png`, его отдельный Core-контракт
  остаётся открытым. Для готового MP4 используются декодированные PNG
  и `prepare/seal`. Восстановление и старт заново имеют операторский путь,
  а условия остановки AE и разрешения на сохранение проверяются отдельно.
  Изолированный AME остаётся отдельной работой из-за общей очереди.

## 8 ноября. Аудит визуальной приёмки без реализации

**Итог консультации:** после нового прямого поручения запрос visual acceptance отправлен в указанную существующую беседу Argon; после восстановления browser connection полный ответ получен без нового send. Verdict `go` с P0-уточнениями provenance, full-size PNG decode, frame-index selection и Titles ROI. Все7 bindings совпали; семь findings локально разобраны, неточности о crop/модулях уточнены. Рекомендация — небольшой внешний `prepare`/`seal` workflow, typed PNG-export позже по потребности. Код не менялся. [Ответ и решения](../reviews/argon/visual-acceptance/20261108-research-01/decisions.md). Прежние сбои ниже сохраняют историю.

### Progress

Исследованы Core `d5bf682…`, legacy `release-3.3.5` на `5d0d255…` и source snapshots Surehand, Engine Room, JUNKDOGE. Сверены saved MP4/PNG, просмотрены три S1 PNG и шесть кадров, извлечённых из точного async MP4 `a6e9e225…`. [Полный отчёт](../docs/visual-acceptance-audit-20261108.md).

### Decision Log

Core имеет render/structural/media verification и отдельные реальные visual checks; общего повторяемого visual acceptance workflow нет. Минимальный следующий implementation scope — внешний review packet готового артефакта с явными frames, ожиданиями и sampled verdict, с выборочным переиспользованием legacy. Typed PNG-export нужен отдельно при потребности в live/lossless capture. Реализация не входит в поручение аудита.

## Исходные install milestones (история; актуальная очередь выше)

1. **Package/status/inspect.** Production composition root `runtime/stdio-entry.js`, реальный HTTP long-poll peer внешнего Node и pure CEP browser, fixed reviewed executor registry, MCP status без lifecycle и bounded typed inspection/discovery. Отдельный CEP bundle `com.codex.aeagentcore4`, видимое имя AE Agent Core4.0.0. Receiver/store во внешнем Node; browser не исполняет Core через embedded Node17. Installer публикует immutable release по manifest hashes, отдельные credentials и project MCP entry, сохраняет state origin/fences. После scoped subprocess/IPC/VM/package/installer regressions — bounded review, commit и root install/read-back.
2. **Typed manual current-target.** Отдельный optional `titles-current-target` package/contract с target без sessionId. Private branded policy вне domain-neutral Core; engine-optional single-step path и versioned resource scope. Generic inspect→build→proposal→dry-run→run; fresh native confirm, single setter и local transaction receipt verifier. Durable preimage checkpoint покрывает точный текст/объявленный style, не весь AEP; recovery требует нового typed proposal/подтверждения. Политика выбирается trusted composition/admitted pin, не public Boolean. Default automatic epoch gates сохраняются. После scoped regressions/review обновить пакет и установленную копию.
3. **Фактическая приёмка.** Correlated MCP handshake, exact Node/install/CEP identities, status/admission coverage, одна разрешённая read-only инспекция через installed IPC. Для mutation — актуальные resource/ownership/physical gates и native confirmation. Если running AE не позволяет загрузить новую панель без сохранения/перезапуска, не закрывать его автоматически и не объявлять offline PASS живым результатом; независимая source/packaging работа продолжается.
4. **Двусторонняя переносимость и обновления.** Выполнить этапы [постоянного контракта](../docs/portability.md): матрица сред и installer gaps → адресная реализация/preflight/config generation → реальный десктоп→MSI→десктоп цикл → отчёт P1–P8. Повторная ручная настройка не допускается; credentials/state/authority остаются локальными, общие fences сохраняются. Критерий обязателен до объявления готовности выбранного состава, а не отложен в необязательные улучшения.

Между пунктами не нужны новый чат и повторное разрешение на уже порученную разработку/установку. Каждый пакет самостоятельно запускает свой разрешённый scope. После первого status-only результата работа продолжается ко второму пункту. Добавление пункта 4 в план не возобновляет остановленные live/UI-действия и не выдаёт доступ к другой машине.
