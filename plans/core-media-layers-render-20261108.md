## Журнал решений

### L1. Вставка медиа в существующую композицию

1. Сделать отдельный типизированный импорт `media.import` и действие
   `layer.insert` для уже существующего project item. Допустимые источники
   вставки — файловый still, AV-файл и прекомп без цикла зависимостей. Входы
   определяют AEP/сеанс, comp ID, source item ID, `above/below` и anchor layer ID,
   диапазон и, при необходимости, явную 2D-трансформацию. Выход возвращает ID
   созданного объекта. Для сгенерированных фото подготовка кадрирования,
   масштабирования и GPT Image остаются шагами внешнего workflow.
2. Повторно сверять исходный файл и локальный путь, целевые IDs, ревизию, стек
   и матты после подтверждения. Сохранить однотипный для Core маршрут
   inspect/build/propose/dry-run/run/read-back, точный допуск и ES3-исполнитель.
   Стек проверять по относительному порядку ID всех исходных слоёв, а для нового
   слоя — по источнику, соседу, видимости, диапазону и трансформации. Для маттов,
   родительских связей и выражений с индексами отдельно доказать поддержку либо
   отказать до записи с объяснением. Проверить влияние на каждую сцену,
   использующую общий прекомп.
3. Импорт и вставка имеют отдельные квитанции. При успешном импорте и отказе
   вставки свежая проверка должна позволить использовать выданный item ID без
   нового импорта. При неопределённом исходе блокировать повтор до сверки
   исходной квитанции, инвентаря и стека. Удаление частичного результата —
   отдельное решение для однозначно принадлежащего задаче объекта.
4. Существующие фото и сборку сохранить совместимыми. После L1 взять отдельный
   срез дублирования слоя с заменой источника, если реальный шаблон требует
   наследования масок, эффектов, анимации или родителя. Для L1 достаточно
   воспроизводимого размещения нового слоя с явным кадрированием.

### R1. Рендер по постоянному ID задания

1. Новый контракт `prepare → start → status → finalize`. Точная comp по ID,
   вся длительность или полуоткрытый диапазон кадров, локальный профиль
   формата и новый путь назначения. Сохранить существующий `comp-render`
   для Titles/Slideshow. Начальная поставка R1 — H.264 MP4 со звуком при наличии
   в исходнике; контракт профилей позволяет добавлять форматы с собственной
   проверкой. Длительность ограничена валидным диапазоном AE и доступными
   ресурсами. Ограничения размера снимка и числа одновременных заданий
   задаются отдельно.
2. Предпочтительный кандидат — отдельный процесс `aerender` без `-reuse`
   на проверенной, явно сохранённой рабочей копии. На копии требуется
   однозначный выбор цели: уникальное имя, связанное с comp ID, и отсутствие
   конкурирующей строки для этой же comp, либо доказанный эквивалент.
   Всегда передавать явную композицию. Определить допустимый способ подготовить
   копию, зафиксировать её SHA-256, доступность зависимостей, пресет и
   выходную бронь. Проверить свойства ссылок при переносе AEP, активный
   AE, лицензирование, плагины, шрифты и локальный H.264. Выбор исполнителя
   остаётся условным до проверки этих рисков. [Семантика aerender у Adobe](https://helpx.adobe.com/after-effects/desktop/render-and-export/automate-rendering/automated-rendering-network-rendering.html)
3. Хранить intent до запуска, ID задания и попытки, identity процесса и
   подтверждение запуска, статус и неизменяемый терминальный receipt.
   Процесс работает вне окна ответа MCP/CEP. `status` восстанавливает
   наблюдение после перезапуска клиента/owner. При обрыве между spawn и
   receipt сверять процесс и артефакты; неопределённость блокирует повтор.
   При проверке отмены действовать только на подтверждённое дерево процесса.
   Свой временный выход публиковать после проверки и без перезаписи
   существующего файла. Остановку, частичный файл и завершённый выпуск
   отличать по состоянию процесса, квитанциям и независимой проверке медиа.
4. Исторический AME `exportItem` затронул общую очередь. AME и синхронный
   CEP остаются за границей R1. Если изоляция выбранного исполнителя на
   стенде не подтвердится, оставить существующую поставку и пересмотреть
   backend до открытия новых команд. [Наблюдение по общей очереди](titles-end-to-end-msi-20261105.md#L682)

#### R1a. Сохранённый AEP полного мастера

- **Progress.** 10 ноября на MSI реализована потоковая проверка и копирование
  сохранённых AEP до 96 МиБ в локальном `aerender-jobs`.
- **Decision Log.** Существующий локальный CLI уже ведёт задания по ID,
  записывает намерение и проверяет MP4 перед публикацией. Его предел 64 МиБ
  исключает проверенный AEP десктопа размером 95 724 372 байта. Первый
  блок R1 принимает сохранённые AEP до 96 МиБ включительно через штатную
  потоковую проверку Core. Побайтная рабочая копия остаётся рядом с AEP
  ради относительных ссылок. Перед выдачей сверяются SHA исходника и копии.
  Сохраняются прежний формат заданий, явный выбор готовой строки очереди,
  правила UNKNOWN и публикации. `comp-render` остаётся доступен прежним
  продуктам. Подготовка очереди, восстановление наблюдения после смерти
  worker, аудиопрофиль и диапазоны идут отдельными блоками.
- **Validation.** Scoped `aerender-jobs` прошёл 6 тестов. Временные файлы
  подтвердили 96 МиБ и отказ на 96 МиБ + 1 байт, совпадение SHA копии,
  отказ до dispatch при изменении байта без изменения размера и сохранение
  копии при сбое очистки временной ссылки после публикации квитанции.
  Совместный прогон с `comp-render` дал 16 PASS. Нативный рендер R1 открыт.
- **Следующий блок.** Восстановить наблюдение по тому же ID, когда worker
  исчез, а исходный процесс рендера продолжает работу. Привязать наблюдение
  к исходной выдаче и identity процесса. При недостаточном доказательстве
  сохранять UNKNOWN и блокировку повтора.

### Поставка и порядок

После одного Argon review разобрать замечания в журнале решений. Затем
реализовать L1 и R1 как два отдельно проверяемых этапа. Использовать
декларации составов, hash pin артефакта и существующие профили результата,
где их инварианты совпадают. Привилегированное чтение файлов, запуск
процесса, бронь путей и журнал остаются в доверенной части. Доменное
сопоставление слоёв и параметров относится к модулю. Каждый новый профиль
получает адресные тесты и проверку установленного обнаружения на десктопе.
Отдельная проверка переноса проводится при изменении его механизма или
условий среды либо при конкретном сбое.
[Поставка модулей](core-modularity-pilot-20261106.md#как-добавить-операцию-с-существующим-профилем) · [Переносимость](../docs/portability.md)

## Валидация

- Аудит выполнен по исходникам и ответам `core_status`, `list_modules` и
  четырём `get_module_contract` из штатного MCP MSI. Lease для аудита не
  брался. Исторические нативные прогоны использованы с привязкой к дате и
  пакету. Для текущего этапа достаточно статической проверки и MCP discovery.
- Для L1 проверить дубли имён, изменения стека после dry-run, чужой/пропавший
  item, переиспользование импорта, матты, отказ после частичной записи и
  совпадение старых layer IDs/порядка. Затем визуально проверить несколько
  слотов на рабочей копии и известные использования их прекомпов.
- Для R1 проверить полный мастер, который одновременно длиннее 12 секунд
  и больше 600 кадров, диапазон с дробным fps и ненулевым стартом,
  пересечение выходных путей, недоступный пресет, зависимость/шрифт,
  обрыв после spawn, перезапуск наблюдателя, отмену и повреждённый выход.
  Сравнить настройки и состояние чужих заданий. Независимо декодировать
  MP4 и проверить длительность, кадры в начале, на переходах и в конце,
  звук при его наличии. Проверить совместимость коротких Titles/Slideshow.
- Финальная нативная приёмка проходит на DESKTOP-32974QF после штатной
  сборки, обновления и read-back. Реальный AEP, фото и
  референсы остаются в локальном рабочем контуре. Подготовка плана не
  включает реализацию, установку или изменения проекта AE.
