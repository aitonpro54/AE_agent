# C1b. Отдельная поставка операции Titles

5 ноября 2026, MSI. Первый пакет операции — `titles-current-target`.
Основание — [план внешних продуктов](external-products-titles-20261029.md#очерёдность)
и [принятый нативный прогон T2](titles-live-20261029.md#5-ноября-titles-на-core-410).

7 ноября этот же CLI получил [поддержку допущенных слотов декларативных составов](core-modularity-pilot-20261106.md#7-ноября-отдельное-обновление-допущенных-операций-c1c).
Показанные ниже команды сохраняются. Для других слотов укажите их собственные
каталог модуля, допуск и проверенную базу.

## Progress

- `core4/tools/package-capability.js` упаковывает четыре файла операции в
  переносимый JSON и выдаёт SHA-256 манифеста. Поставщик может подготовить его
  из отдельного каталога. В пакете находятся артефакт, контракт, builder и JSX.
- Сборка требует три закреплённых входа: базовый `manual/owner` пакет Core 4.1,
  отдельно поставленный пакет операции и отдельно проверенную запись допуска.
  Она проверяет файлы и зависимости, сопоставляет контракт с существующей
  операцией, обновляет её запись каталога и пересобирает фиксированный реестр CEP.
- При изменении модуля standalone-манифест фиксирует хеш исходного пакета.
  Bootstrap допускает `owner-update` и его продолжение только с этим хешем
  текущей установки. Обычные `apply` и `dry-run` для такого дистрибутива
  отклоняются. При побайтно совпадающем модуле и допуске сборка возвращает
  исходный пакет и обычный манифест.

## Decision Log

- Выбран один существующий слот с точным прежним публичным контрактом и
  политикой `current-matching-target-after-local-confirmation-v1`.
  Новый контракт, эффект или зависимости требуют отдельного рассмотрения.
  Версия артефакта может меняться. Смена module pin требует пересмотра
  совместимости внешнего компилятора Titles, который явно закрепляет pin.
- При сборке весь Core берётся из уже проверенного базового пакета. Меняются
  только файлы выбранной операции, её допуск, каталог и сгенерированный JSX
  реестра. При изменении байтов получается новый hash **установочного состава**.
  Startup, HTTP, формат журналов, серверная политика и транспортные привязки
  используют прежний код. Обновление применяет штатный остановленный оператор
  с отдельным enable. Горячая подмена работающего исполнителя в этот срез не входит.
- Доверенный SHA-256 базы, пакета и байтов записи допуска передаёт оператор
  после проверки соответствующих материалов. Самоописание поставщика и
  автоматически вычисленный им хеш не заменяют проверку и запись допуска.
  Изменяемый JSX сам выполняет native confirmation, повторное сравнение цели
  и запись. Проверка каждой версии допуска должна покрывать эти гарантии и
  отсутствие побочных действий при загрузке и чтении. Сборщик после проверки
  допуска проверяет экспорт `build`, три функции JSX и загрузку реестра с
  его собственным JSON-кодеком в
  Node VM без портов AE. VM проверяет форму доверенного кода. Приёмка нового JSX
  в After Effects остаётся отдельной проверкой конкретной версии.
- Работа над C1b ведётся на MSI. Чтение десктопа относилось к поиску материалов.
  Сводный пакет правил из десктопного чата и каталог исходников приняты в
  `25c1129`. Перенос установленной сборки относится к будущему этапу.
  [Каталог Titles](../docs/titles-legacy-inventory-20261105.md).

## Сборка

В примере `$baseCandidate` — абсолютный путь к `candidate.json` уже проверенного
standalone Core 4.1 `manual/owner`. `$basePin`, `$capabilityPin` и `$admissionPin`
получены из проверенных источников. `$reviewedAdmission` указывает на запись
с допуском точных байтов операции и её контракта. Родительские каталоги
существуют, пути `$capabilityFile` и `$candidateDirectory` новые.

```powershell
node core4/tools/package-capability.js pack `
  --source $moduleDirectory --output $capabilityFile

node core4/tools/package-capability.js compose `
  --base $baseCandidate --expected-base-hash $basePin `
  --capability $capabilityFile --expected-capability-hash $capabilityPin `
  --admission $reviewedAdmission --expected-admission-sha256 $admissionPin `
  --output $candidateDirectory
```

`pack` читает точный каталог с `artifact.json`, `contract.json`, `executor.jsx`
и `implementation.js`. Для текущего встроенного источника запись допуска лежит
в `core4/config/admissions/titles-current-target.json`. `compose` выводит
`distributionHash` и `packageHash`. Обновление выполняется по инструкции
`README.txt` нового дистрибутива. В `--expected-current-package-hash` передаётся
тот же `$basePin`, в `--expected-package-hash` — новый `packageHash`. Если
`packageHash` совпал с установленным,
обновлять состав ради повторной упаковки не требуется.

## Validation

- Обычный CLI из другого рабочего каталога упаковал текущий `titles-current-target`
  в `7ac768b2…`. Повторная сборка с известным допуском воспроизвела опубликованный
  пакет `3de578fb…`. Standalone `12f13ad8…` содержит 98 файлов, в том числе новый
  bootstrap с проверкой исходного пакета.
- Сквозной TEMP-тест использует другую версию артефакта и другой SHA-256 JSX при
  том же контракте. Проверяет отказ при неверном пине, повреждении, чужом или
  отозванном допуске, смене эффекта, базе `readonly`, отсутствии функций и
  попытке обновить другую совместимую установочную базу. Проверяет точную дельту
  файлов, штатные остановленный update и enable, выбор нового module pin,
  прежние installation ID, state path, origin, receiver и ledger.
  Наблюдения процессов в тесте синтетические. Установочный CAS и файловый
  read-back настоящие. Рабочая установка MSI не переключалась.
- Независимое ревью нашло незакреплённую базу установки и риск сбоя при
  загрузке синтаксически корректного реестра. Повторная проверка на финальных
  байтах подтвердила отказ на другой базе, отсутствие функций и сбой
  инициализации с собственным JSON-кодеком CEP. Два промежуточных прогона
  `stopped-update` прерваны перед изменением исходников. Для итогового
  покрытия используются только результаты по финальным байтам.
- Шесть канонических сопутствующих проверок прошли 58 случаев: `stopped-host-readoption-operator`
  17, `stopped-update-operator` 4, `maintenance-finish-operator` 7,
  `standalone-installer` 7, `owner-installation` 18 и `validation-routing` 5.
  Проверка границ Core прошла 55 проверок, `git diff --check` прошёл.
- Полный `stopped-update` прошёл 56/56, включая C1b. Всего по семи выбранным
  проверкам 114 успешных случаев без падений, отмен или пропусков. Сохранены
  `accepted-stopped-update.log` и `accepted-supporting.log` в локальном каталоге
  `snapshots/c1b-capability-20261105/`. Проверки более широкого выпуска не входят
  в этот результат.
