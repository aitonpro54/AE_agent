## Цель и неизменные условия

- Заполнить необходимые плейсхолдеры открытого AE-проекта локальными видео из `C:\Проекты 21\2026.10.18 - Музыка компьютерных игр\трейлеры`. Файлы уже скачаны; поиск YouTube и скачивание исключены.
- Для каждого принятого в scope плейсхолдера подготовить **два отдельных прекомпа по 7 секунд**. Способ их включения в существующие слоты/слои определить по структуре проекта; не подменять это одним 14-секундным компом.
- **Каждый из двух прекомпов обязательно сочетает минимум два разных исходных видео.** Разные отрезки одного видео или его переименованные копии условие не выполняют. В монтажном описании сохранить исходные файлы, полные SHA256 и диапазоны каждого шота.
- Предварительная раскладка каждого прекомпа: `[0,2) + [2,4) + [4,6) + [6,7)` секунд, то есть **2+2+2+1 без пустот**. После определения fps выразить границы целыми кадрами, точно покрыть принятый семисекундный интервал и записать фактическую длительность; округление не оставлять скрытым. Большинство шотов остаются около 2 секунд.
- Выбирать фрагменты без видимого текста: титров, субтитров, текстовых логотипов и читаемых игровых надписей в конечной области кадра. Проверить весь используемый отрезок, а не один удачный стоп-кадр.
- Персонажи должны органично смотреться в конечном видимом кадре. Лица не обрезать; обрезка тела на уровне торса допустима. Учитывать движение персонажа/камеры, маски, perspective и трансформации всех родителей.
- Окончательная визуальная приёмка — в **Split Scene 05**, а также в других фактически использующих изменённые цели сценах. Изолированный placeholder или прекомп не заменяет итоговый вид сцены.
- Сохранить исходники, исходный AEP, ручные пользовательские правки, анимацию шаблона и существующий звук. Рабочая копия/checkpoint и финальное сохранение проходят штатные lifecycle gates. Финальный render и публикация в этот scope не входят.

Рабочие контракты: [монтаж](../docs/montage-workflow.md), [маршрутизация](../docs/model-routing.md), [Tool-First](../docs/tool-first-workflow.md), [сводка завершения](../docs/ae-task-completion.md). Перед live-работой прочитать `ae-safe-project-automation`; для Flash — `antigravity-cli` и его AE reference.

## Организация работы и артефактов

Диспетчер сохраняет единый manifest и назначает **одного AE/CEP/UI controller**. Максимум два активных helpers суммарно, включая AGY. Остальные работают по зафиксированному snapshot; применение изменений всегда последовательное. После сложного блокера исполнитель выбирается заново по scope.

| Блок | Исполнитель и ownership | Основание |
|---|---|---|
| Инвентаризация файлов, простая сводка | Luna/high `ae_scout`, отдельный каталог | Независимые read-only данные; live-чтения делает controller |
| Анализ шотов и подготовка своей группы | Sol 6.1/high и Flash `gemini-3.8-flash-high`, configured High | Пользователь явно назначил Flash на часть плейсхолдеров; группы определить после инвентаризации |
| Scoped сборка, техническая проверка и исправления | Sol 6.1/high `ae_implementer` | Последовательная реализация с передачей sole control, если она нужна |
| Итоговая приёмка сцен | Диспетчер по evidence исполнителей | Проверка полного покрытия и реального просмотра |

Параллельный вариант: Flash готовит группу A, Sol — независимую группу B в разных директориях; никто не переписывает чужие материалы и canonical manifest. Их задания содержат один snapshot, исходный запрос, точные группы/границы записи, критерии, ожидаемые артефакты и запрет live-доступа. Native поручения — `fork_turns: none`, дальнейшая делегация запрещена. При занятых двух слотах новый helper не создаётся.

На применение выдаётся один принятый пакет за раз. Если Flash получает live-часть своей bounded группы, controller передаётся ему явно только после сверки pending/inflight; параллельный Sol остаётся offline. Диспетчер не дублирует подготовку той же группы.

Все рабочие данные хранить в ignored `.codex-runtime/game-trailers-montage/`, без архивов evidence в Git:

- `inventory/project-snapshot.json`, `inventory/source-catalog.json` — observedAt, project identity/revision, stable IDs, связи, метаданные и полные хеши источников.
- `work/sol-<group>/`, `work/flash-<group>/` — независимые монтажные описания, просмотренные кадры/contact sheets и подготовленные материалы с provenance.
- `montage-intent.json` — каноническое описание двух прекомпов на цель, шотов/исходников, source in/out, кадровых границ, crop/scale, ownership и ограничений.
- `manifest.json`, `prepared-materials.json` — только если применим штатный V1: строгие схемы `ae-agent-montage-manifest.v1` и `ae-agent-prepared-materials.v1`; дополнительные provenance/учёт хранить отдельно, не добавлять неизвестные поля API.
- `frame-plan.json`, `evidence/index.json`, `runs.json`, `acceptance.json` — покрытие кадров, ссылки/хеши действительных PNG из штатного server export root, run IDs, read-back и раздельные статусы execution/technical/visual.
- `usage/` — снимки доступного учёта, временные интервалы, coverage и краткие выводы. Артефакты существующего bridge остаются в его штатном ignored runtime; индекс ссылается на них.

## M1. Инвентаризация и план шотов

1. Controller читает свежие bridge/project/lifecycle state и точную активную композицию; фиксирует путь AEP, dirty/revision, доступность защиты и чужие pending-команды. Не открывает другой проект и не сохраняет текущий вслепую.
2. Через `search_solutions` → нужные `get_solution` определить поддержанные typed пути для создания/наполнения двух прекомпов, импорта, timing, замены и crop. Наличие recipe в документации не считать проверкой текущего runtime.
3. Адресно обследовать `Split Scene 05`: stable comp/layer/source IDs, реальные placeholder slots и число целей, видимые интервалы, размеры/PAR/fps, nested startTime/stretch/remap, маски/effects/parents и все shared uses. Для placeholder — `get_layer_details(responseView:"placeholder")`; недостающие поля — точечные reads.
4. Составить локальный source catalog: точные пути, duration/fps/resolution/PAR, полнота декодирования, SHA256 и реально доступные диапазоны. Имена файлов сами по себе не подтверждают игру/группу. Ничего не импортировать и не переименовывать на этом шаге.
5. Выбрать нужные цели и две семисекундные последовательности на каждую; записать ≥2 различных видео в каждой, согласованность игры/содержания, порядок шотов и безопасные позиции лиц. Не навязывать полную уникальность всех видео между разными прекомпами, если её не требует шаблон/политика.
6. Заранее составить план проверки начала/последнего видимого кадра, каждого шота, обеих сторон всех стыков и важных движений. Времена перевести в root-time `Split Scene 05` с учётом вложенных преобразований; неизвестный remap не заменять предположением о линейности.
7. Разделить непересекающиеся группы Sol/Flash, желательно сопоставимые по сложности. На первом небольшом пакете Flash подтвердить **фактический доступ к нужным изображениям и их просмотр**: exact files/times/hashes, наблюдения о тексте, лицах и движении. Metadata и transport SUCCESS не являются visual pass.

VideoScout использован для локальной подготовки после десятиминутного окна восстановления bridge. Его scoped `Code/AGENTS.md` и `media-access.md` прочитаны; профиль `videoscout`, отдельные права и local-only входы проверены. Фактический просмотр Flash подтверждён для предоставленных PNG; непрерывный просмотр MP4 и прослушивание не подтверждены. AE grants не переносятся, YouTube/download flow исключён.

**Выход/приёмка M1:** подтверждённый перечень целей и связей, source catalog, montage intent, frame plan, распределение групп и известные blockers. Если fps дробный и ровно 7,000 секунд не лежат на кадровой сетке, выбрать ближайшую допустимую границу по фактическому шаблону и явно записать отклонение; существенный конфликт с требованием 7 секунд разрешить до применения, без скрытого ретайминга проекта.

## M2. Подготовка материалов по группам

Sol и Flash независимо подготавливают свои монтажные описания/материалы по snapshot. В каждом шоте указать исходный файл и SHA256, исходный диапазон, место на семисекундной шкале, intended crop/scale и просмотренные контрольные кадры. Проверить текст и лица на всём отрезке, в том числе в движении; сомнительный фрагмент заменить другим локальным кандидатом.

| Вариант сборки | Цена и ограничение | Решение |
|---|---|---|
| Два нативных AE-прекомпа с отдельными слоями исходных шотов | Сохраняет редактируемость; больше typed операций, требуется подтверждённый контракт создания/timing/relink | Предпочтителен, если существующие tools покрывают структуру |
| Два подготовленных 7-секундных montage clips, каждый внутри отдельного AE-прекомпа | Дополнительное локальное кодирование и проверка качества; уплощает шоты, сохраняет provenance отдельно; нельзя выдавать два footage за два прекомпа | Допустимый запасной путь существующей material preparation, если он лучше соответствует поддержанному subset |

Новый продуктовый pipeline, зависимости и Full Intaker ради этой задачи не нужны. `build_montage_pipeline_plan` не считать универсальным сборщиком multi-source прекомпов: он компилирует поддержанный replace/timing/framing subset. Для shared targets, нелинейного remap, неподтверждённых групп или иной несовместимости использовать только подходящие существующие typed планы либо вернуть точный blocker, сохранив независимую подготовку.

При нормализации fps/PAR/размера создавать новые производные в своей директории, не менять оригиналы. Зафиксировать команды существующих инструментов, параметры, фактические duration/fps/dimensions и полный SHA256 результата; не устанавливать пакеты. У каждого подготовленного clip сохранить соответствие всех шотов оригиналам. Два повторных пути к одному видео не считать разными источниками.

Для AGY: профиль `ae-agent`, уникальный task ID, исходный текст в `original_request`, точные `material_refs`/`required_inputs`, команды поштучно в `required_commands`, артефакты в `expected_artifacts`. Не придумывать `original_request_file`, не использовать случайный `--continue`; продолжение — новый task ID и explicit conversation ID завершённого хода. Проверить status/schema/artifact flags и фактические файлы отдельно от visual acceptance.

**Выход/приёмка M2:** принятые пакеты обеих групп, закрытые 7 секунд без пропусков, различие источников внутри каждого прекомпа, проверенное содержимое и согласованный manifest. Если Flash не может видеть кадры, сохранить этот пробел, не засчитывать художественную работу; после проверки остановки процесса/эффектов передать зависимую визуальную часть Sol/high и честно отразить ограничение сравнения.

## M3. Последовательное применение и кадрирование

1. Перед первой записью создать предусмотренную protection/checkpoint или рабочую копию с сохранением исходного AEP через доступный штатный механизм. Save As — отдельный lifecycle plan с exact manual CEP confirmation и native read-back пути/identity; автономная сессия не отменяет этот gate.
2. Перед каждой группой controller сверяет fresh project/target identities, исходные источники и защищённые поля с manifest. При ручных правках пользователя обновляет затронутый baseline, сохраняет эти правки и пересобирает только устаревшие назначения. Snapshot не даёт права перезаписать более новое состояние.
3. Создать/наполнить два прекомпа на цель и привязать их к подтверждённым слоям по существующему typed контракту. Проверять новые IDs после создания; индексы не кешировать между мутациями. Имена/папки согласовать с текущим шаблоном, ownership записать до cleanup.
4. Каждый пакет: builder → `propose_ai_agent_plan` → настоящий dry-run → run с точными текущими action/revision/hash и действующими gates → адресный native read-back. При применимости V1 — `build_montage_pipeline_plan({manifest,preparedMaterials,budgets})`, отдельный proposal на unit, затем `reconcile_plan_run.montageReadBack` и M3 summary. Missing reads не дают technical pass.
5. Проверить длительности/кадровые границы, источники всех шотов, непрерывность покрытия, crop/scale, сохранность masks/effects/animation и зависимых сцен. Корректировать ограниченную цель, затем обновлять её read-back и затронутые кадры.
6. При partial/timeout/unknown сначала status, процесс, файлы, pending/inflight и фактическое AE-состояние. Сохранить завершённые шаги и продолжать только сверенный остаток; imports/creation/replace не повторять вслепую. Передача controller допускается после выяснения исхода.

Один блок может включать несколько планов; `maxSteps` должен покрывать заявленный пакет, без усечения результата. Компактные ответы допустимы при сохранении полной серверной проверки. Отказ gate не обходить raw JSX, GUI, другой моделью или провайдером. Frozen intake/importer/supervisors, продуктовый код, зависимости и provider settings не менять ради монтажа.

**Выход/приёмка M3:** два действительных 7-секундных прекомпа на каждую цель, traceable multi-source монтаж, receipts/run IDs, адресные свежие reads и technical status. Это ещё не окончательная художественная приёмка.

## M4. Приёмка Split Scene 05 и завершение

- Получить PNG по заранее заданному frame plan через штатные visual builders/`save_comp_frame_png`, соблюдая реальные лимиты батчей и gates экспорта. Просмотреть действительные файлы в читаемом размере; хеш/валидность PNG не доказывают просмотр.
- Для **каждого** из двух прекомпов каждой цели проверить в итоговой `Split Scene 05`: начало, последний видимый кадр, представительный кадр каждого шота, кадры непосредственно до/после всех стыков (предварительно 2/4/6с в local time), изменения crop и важные положения камеры/персонажей. Exact outPoint исключён из видимого интервала.
- Движение проверить просмотром доступного локального preview/последовательности кадров в нужных интервалах, уплотняя sampling на движущихся лицах и появлении текста. Одного middle frame недостаточно; полный финальный render для проверки не требуется. Если доступен только sparse sampling, указать остаточный пробел и не принимать движение целиком.
- Критерии: нет пустот/чёрных кадров и нежелательных вспышек, текст не виден, лица не обрезаны, тела допустимо обрезаны по торсу, масштаб и композиция органичны в финальном split-окне, переходы и анимация шаблона сохранены. Проверить также все фактические uses изменённых shared целей.
- После исправления источника/timing/crop/родителя/effect/matte инвалидировать приёмку изменённой цели и всех использующих сцен, обновить их evidence. Неизменённый уже просмотренный PNG можно переиспользовать только при том же хеше и релевантном состоянии.
- Диспетчер принимает покрытие целиком, сохраняя отдельные transport/execution/technical/visual статусы и причины отказов. Собрать штатную локальную completion summary по явным run IDs; её `provided_run_ids_only` и `machineProofOfViewing:false` не превращать в полную приёмку.
- Финальное сохранение принятой рабочей копии выполнить только через предусмотренные gates и подтвердить actual path/state. Исходный AEP не перезаписывать. Render queue и публикацию не запускать.

**Выход/приёмка M4:** сохранённая принятая версия AEP, manifest/каталог материалов, coverage и просмотренное evidence по каждой цели, список исправлений/ограничений и итоговый учёт. Непросмотренная цель остаётся незавершённой.

## Учёт времени и токенов

Записывать по исполнителям фактические start/finish и периоды подготовки, AGY/model run, ожидания, применения, проверок и исправлений; отдельно учитывать dispatch/проверки родителя. Общая длительность — wall-clock от начала до конца, а не сумма пересекающихся интервалов helpers. Человеческое ожидание и вычисления различать при наличии timestamps; неизвестное не распределять предположительно.

Расход читать локальными read-only `get_task_usage`/`get_usage_history` Codeburn при закрытом AE по проектному контракту. Во время монтажа сохранять доступные metadata и таймстемпы, а Codeburn сверять в разрешённый момент; не закрывать рабочий AE только ради замера. UUID текущего чата подтверждён родителем из runtime: `01a13efb-07c2-73b0-a013-c6f17de9e3e4`; не брать ID из окружения общего MCP, не использовать `current`. При доступности включать children; `input/cached/output`, model/effort и AGY usage брать из фактических metadata, отсутствующие поля оставлять unknown.

У каждого снимка сохранять `collected_at`, период, coverage и пропуски, недоступные child/AGY данные и факт, что текущий незавершённый ответ может ещё отсутствовать. Снимок `usage-planning-snapshot.json` с `collected_at: 2026-10-15T09:59:56Z` — промежуточный накопленный учёт чата (8 записанных ответов), **не нулевой baseline монтажа**. Перед исполнением нужен новый снимок; затраты подготовки плана включать в task настолько, насколько позволяет фактическая гранулярность.

Сравнивать Sol/Flash по принятому плейсхолдеру и принятому 7-секундному прекомпу с указанием сложности, качества, числа итераций и затрат контроля/исправлений. Разные группы не являются контрольным экспериментом: экономия без контрольного прогона — лишь оценка. Quota относится к аккаунту; AGY учитывать отдельно, не приписывать account quota одному task и не переводить токены в недельную квоту без данных. Сбор автоматический, отчёт — по запросу/в финале; монитор или автоматизацию не создавать.
