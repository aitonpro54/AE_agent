# Оценка курса модульности AE Agent Core

Review ID `20261106-plan-01`, stage `modularity-course`, тип `plan`.
Snapshot `1c32744eaa944451d9b4ae8e5856bbcadee7763e`, Core 4.1.1, MSI, 6 ноября 2026.

Пользователь просит оценить отклонения от принятого курса, способы оптимизации и получить консультацию Argon. Текущий scope — анализ и рекомендации. Реализация рекомендаций потребует отдельного рабочего этапа.

## Исходный критерий

26 октября принят замысел небольшого постоянного Core, независимых пакетов операций и проверок по изменённым компонентам. 29 октября выделены внешние продукты Titles/Slideshow. Изменение шаблона или переноса строк должно оставаться в продукте. Добавление AE-возможности требует допуска и проверки соответствующего исполнителя. Цель — уменьшить стоимость изменений, повторных проверок и контекста.

## Установленные факты

- Продукт Titles действительно вынесен в products/titles. Он готовит JSON для существующего MCP, не импортирует private Core. Шесть нативных capabilities в установленном manual-titles-variants/owner. В source catalog есть ещё два старых модуля без текущего native route. Общий MCP содержит 19 generic/control команд.
- Owner отделён от клиентского подключения, есть устойчивые журналы, checkpoint, исходные receipts и запрет повторять неизвестную мутацию. На MSI приняты реальный текст, вёрстка, варианты и MP4. Реальный 3D derive и изолированный AME остаются открытыми.
- validate-diff выбирает owner, объявленные public/shared consumers и component dependencies. Ключ evidence учитывает команду и bytes зависимостей. Интеграции, затронутые вне выбранного маршрута, получают deferredCoverage/current-closure-unverified. Автоматический replay тестов по cache в --run отсутствует, reuse выполняется при разборе сохранённого evidence.
- В текущей карте 75 named checks. Выбор без запуска тестов для executor+artifact+admission text-variant или comp-render даёт 1 selected и 33 deferred. Для broker.js 26 selected/19 batches/22 deferred. Для protocol/json.js 34/27/29. Изменение package-installable.js+stdio-entry.js+source-package.json даёт 27 selected/27 batches/26 deferred. Это число наборов, не test cases и не измерение времени/токенов.
- Runtime имеет явные списки composition IDs и module IDs, отдельные ветви для новых capabilities, импортирует их proof-функции. Эти proof-функции содержат предметные проверки шрифтов, стилей, центровки, анимации и имени titles-output.
- Отдельная поставка C1b поддерживает только существующий слот titles-current-target на базе manual/owner с идентичным публичным контрактом. TEMP-проверка update/enable пройдена. Это ещё не общая поставка любого нового модуля.
- Установочный пакет проверяется целиком и обновляется остановленным stop/update/enable. Сам факт нового package hash разумен для целостности. Его нельзя путать с обязательным повтором всех предметных тестов.
- Карта интеграций содержит широкие зависимости runtime/, core/, modules/, tools/, config/. Часть интеграций действительно строит полный пакет, поэтому простое исключение файлов из хешей было бы недостоверным.

## Предварительная оценка Codex

Направление сохранено, продуктовая граница и локальные проверки уже полезны. Независимость добавления/поставки операций реализована частично. Основной риск — рост предметных веток в runtime и возврат дорогой общей приёмки через широкие fixture dependencies. Предыдущая формулировка «один тест для модуля» описывает лишь локальный цикл, а не всю стоимость выпуска.

## Предлагаемый следующий ограниченный этап

1. Замерить на одной локальной правке набор тестов, длительность, прочитанный объём и причину каждой зависимости. Развести local component validation, установочную интеграцию и полный выпуск.
2. На одной-двух дорогих интеграциях выделить минимальную fixture и dependency closure. Сохранить отдельную полную проверку реального установочного состава. Не сокращать хеши без изменения реальной зависимости теста.
3. Проверить возможность уменьшить перечисления конкретных модулей в stdio-entry/package builder через reviewed декларативный состав и небольшой фиксированный контракт адаптеров. Обязательные допуски, hashes, receipts и fsync остаются. Не превращать manifest в разрешение выполнить произвольный импорт.
4. Разделить чистую предметную проверку результата и привилегированный host/file proof. Проверки файлов и полномочий нельзя механически перенести в недоверенный worker. Сначала один пилот и доказательство границы доверия.
5. Проверить один добавляемый capability на неизменной базе Core, с сохранением public contract и точным описанием необходимых integration checks. Критерий успеха — измеренная стоимость изменения и честная область reuse.

## Данные и границы

INTERNAL — минимальные исходники и инженерная сводка. Сведения эксплуатации сведены к результатам, без AEP, имён заказчиков, путей пользователей, credentials, конфигурации аккаунтов, журналов и raw chat transcripts. В packet только request.md, source excerpts и selector evidence. Полный репозиторий не представлен. Нативные проверки в этом анализе не запускались. Нужен вывод по представленным данным с явным обозначением гипотез.
