F-425-01 [P2] — Отсутствие preflight-проверки staged-файлов .next / .core4-next / .rollback для descriptorPath и configPath в planInstall и до начала записи в rollback

Файл / строки: core4/tools/install-core4.js, строки 31–38 (clientPaths), 274–307 (planInstall), 381–383 (applyInstall), 456–482 (rollback).

Сценарий: Для core-client.json функция clientPaths проверяет отсутствие .next и .rollback на этапе planInstall и в rollbackBinding до взятия lease. Однако для installation.json.next / .rollback (при repeat/update установке, когда assertInitialLayout не вызывается) и для .codex/config.toml.core4-next / .rollback (во всех режимах, включая virgin install, так как configPath лежит вне installRoot) проверка в planInstall отсутствует. Если на диске остался config.toml.core4-next или installation.json.next, то planInstall (и CLI dry-run) завершается успешно, а applyInstall падает с EEXIST только на строках 381–383 — уже после writes = true, записи transactions/<id>-prepared, releases/<hash> и cepStage. Это приводит к удержанию lease (leaseRetained: true) и оставляет артефакты в installRoot. Аналогично в rollback(file) наличие installation.json.rollback или config.toml.rollback обнаруживается на строке 481 уже после перемещения t.cepDir в transactions/<id>-applied-cep (строка 476).

Уверенность: Высокая.

Минимальная проверка: Проверять отсутствие descriptorPath + '.next', descriptorPath + '.rollback', configPath + '.core4-next', configPath + '.rollback' (или их принадлежность текущему staged) в planInstall, assertBaseline и rollbackBinding по аналогии с clientPaths.

F-425-02 [P3] — Использование fs.existsSync вместо entryExists (fs.lstatSync) для cepDir, descriptor и stateDir в planInstall и snapshot

Файл / строки: core4/tools/install-core4.js, строки 141 (snapshot), 277 (planInstall), 398 (applyInstall).

Сценарий: fs.existsSync возвращает false для битой символической ссылки (dangling symlink / junction). Если в virgin-среде по пути cepDir (extensions/com.codex.aeagentcore4) находится битый symlink, строка 277 (fs.existsSync(cepDir)) и snapshot(cepDir) вернут false / null, applyInstall запишет оба origin.json (строки 391–393) и упадёт только при переименовании fs.renameSync(cepStage, plan.cepDir) (строка 399), оставив созданный origin.json и удержанный lease. Кроме того, snapshot(directory) на строке 141 проверяет item.isSymbolicLink() для дочерних элементов, но не проверяет fs.lstatSync(directory).isSymbolicLink() для самого корневого каталога directory.

Уверенность: Высокая.

Минимальная проверка: Заменить fs.existsSync на entryExists на строке 277 и добавить проверку fs.lstatSync(directory) (не symlink / не reparsePoint) в начале snapshot(directory).

F-425-03 [P3] — Остаточные пустые каталоги state/production/broker при сбое virgin applyInstall в окне между acquireInstallLease и writes = true

Файл / строки: core4/tools/install-core4.js, строки 350–356 (applyInstall); core4/runtime/install-lease.js, строки 20–21 (acquireInstallLease).

Сценарий: При первом applyInstall(plan) вызов acquireInstallLease (строка 351) создаёт пустые каталоги installRoot/state/production/broker. Если проверка на строках 353–356 (assertBaseline, assertInitialLayout, assertRuntimeStopped) выбрасывает исключение (например, из-за изменения config.toml параллельным процессом перед взятием lease), writes ещё равен false: releaseInstallLease удаляет install.lock и broker-owner.gate, но пустые каталоги state/production/broker остаются в installRoot. При следующей попытке planInstall на этой же чистой машине сработает отказ existing_installation_without_origin (строка 277). Безопасность identity при этом не страдает (отказ fail-closed).

Уверенность: Высокая.

Минимальная проверка: При необходимости — тест на изменение config.toml между planInstall и applyInstall с проверкой чистоты отката или документированием необходимости пустого installRoot.

H-425-01 [P3] — Молчаливое отбрасывание нестандартных ключей внутри секции [mcp_servers.after-effects-core4] при перезаписи configText
