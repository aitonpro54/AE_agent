## Поручение и предмет

Пользователь предлагает держать слайд-шоу, титры и другие предметные решения вне AE Agent: как самостоятельные фреймворки/проекты, которые пользуются общим AE MCP. Просит сравнить нынешнюю и прежнюю архитектуру, изучить существующие решения и посоветоваться с Argon на максимальном доступном усилии. Это одна архитектурная консультация. Реализация, переустановка, перенос проектов и дополнительные внешние запросы этим review не разрешаются.

## Рабочее предложение для критики

1. Независимые продуктовые workflow-пакеты (условные Slideshow и Titles) владеют пользовательским ТЗ, шаблонами, layout/timing, отбором assets, диагностикой входов, детерминированным построением плана, своими результатами и проверками. Codex skill служит входом; существенная логика существует в коде/схемах/fixtures, а не только в prompt. Отдельный MCP-сервер на каждый такой пакет не обязателен.
2. Между пакетом и runtime — небольшой публичный версионированный протокол и SDK: discovery, чтение ограниченного snapshot, типизированные intents/plans, серверный proposal, dry-run, risk confirmation, execution receipts, verify/reconcile. Пакет зависит от контракта, Core не импортирует пакет при запуске. Точные имена будущих API не объявляются существующими.
3. Core хранит соединение, admission, ресурсные ограничения, актуальные permissions, durable command ledger, UNKNOWN/no-replay и sole controller. Рабочая история пакета и workflow DAG могут быть внешними; Core command ledger и ограничения ресурсов остаются доступны без этого пакета.
4. Редко нужная новая операция AE поставляется как отдельно допускаемое версионированное executor-расширение. Она не означает включение всего продукта в Core и не даёт стороннему пакету произвольный JSX/CEP/credentials. Если хватает существующих операций, host-расширение вообще не требуется.
5. Разделить жизненные циклы workflow, SDK и executor. Сначала один узкий pilot на уже поддерживаемой замене текста, сохранив все текущие gates. Не строить заранее marketplace, plugin PKI, визуальный DAG и universal primitives engine. Отдельные репозитории можно вводить после проверки границы, без массового перемещения исходников.

## Существенные ограничения

- Различать целевую архитектуру, source/offline fixtures, устанавливаемый состав и доказанное live поведение. В текущем составе independent install/hot-swap произвольных модулей ещё не готов.
- MCP обеспечивает интерфейс вызова, но сам по себе не выдаёт authority, идемпотентность, rollback или безопасный retry.
- Внешний workflow не выдаёт grants, не подтверждает собственный успех и не снимает UNKNOWN. Совпадение значения в AE не доказывает завершение неизвестной команды.
- Атомарность многокомандного slideshow и rollback не обещаются. Повтор только остатка после подтверждённых receipts и актуальной проверки зависимостей.
- Две машины имеют локальные credentials/state/authority; двусторонний перенос кода не переносит право исполнить старый plan. Общие AEP/output ресурсы сохраняют ограничения. Реальный round-trip ещё не доказан.
- Отдельный процесс/репозиторий не является sandbox от кода под тем же пользователем. Обсуждается независимость продукта и доверенная установка, не запуск произвольных враждебных plugins.
- Публичные сторонние MCP описаны по первичным источникам; live-тестирования, установки и аудита их безопасности нет. Утверждения авторов не являются нашей приёмкой.

## Вопросы

2. Что действительно следует вынести из прежней и нынешней системы, а что должно оставаться общим? Отличай продуктовую политику от необходимой runtime-authority.
3. Когда достаточно skill + deterministic CLI/library, когда нужен отдельный MCP, а когда нужен host executor? Назови конкретные критерии для слайд-шоу и титров.
4. Как сохранить небольшие typed операции и эффективные batches, не превратив Core в новую библиотеку всех предметных команд и не открыв raw JSX?
5. Какой минимальный внешний pilot докажет независимость обновлений, отказов, receipts и переносимости? Укажи существующие пробелы, которые мешают ему сегодня.
6. Что разумно заимствовать из рассмотренных MCP/Nexrender/Templater/Automation Blocks/Comfy, и есть ли веское основание заменить наш Core готовым решением? Не приписывай продуктам непроверенные свойства.
7. Какие 3–5 решений стоит принять сейчас, а какие явно отложить? Оцени цену сложности и практическую пользу для одного пользователя.
