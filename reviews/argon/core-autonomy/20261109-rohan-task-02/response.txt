Вопрос 1. Root causes и исправления confirmation / read-only timeout / modal readiness; где нельзя обещать автоматическое recovery

Root Cause 1 — Слепота к модальным окнам ОС до входа в ExtendScript: CEP-панель может числиться подключённой по сокету, пока главное окно AE заблокировано модальным диалогом (Missing Fonts, Save Changes, Crash Repair). Root Cause 2 — Смешение исходов чтения и записи (owner_outcome_uncertain на read-only): таймаут project-inspection перевёл Core в глобальный карантин, требующий закрытия AE, хотя операция не мутировала DOM.

Исправление: ввести строгую матрицу состояний запроса:

REJECTED_BEFORE_SEND (не прошёл pre-flight/modal check) — состояние проекта чистое, fence не ставится.

PENDING_READ_TIMED_OUT (запрос без мутации завис в канале) — запрещает новые запросы в канал до тех пор, пока не освободится сокет/канал (чтобы не копить очередь в ExtendScript), но не помечает проект как повреждённый (dirty/uncertain). Как только модальное окно закрыто и пришёл ответ (или подтверждён сброс очереди чтения по request_id), сессия продолжается без перезапуска AE.

COMPLETED_FAILURE (скрипт вернул ошибку из AE) — fence не нужен, состояние известно.

IN_FLIGHT_MUTATION_TIMED_OUT (UNKNOWN_WRITE) — единственный случай, требующий честного owner_outcome_uncertain и сверки состояния/отката к чекпойнту.

Root Cause 3 — Каскадное согласование (restart без проверки dirty, затем save) и расхождение CLI/UI reset: агент пообещал пользователю перезапуск без сохранения до того, как проверил флаг app.project.dirty, что потребовало второго раунда ожидания (1 ч 40 мин). При этом CLI reset требовал baseline-required, а панель разрешала сброс, но была недоступна для Computer Use из-за границы процесса CEPHtmlEngine.

Исправление: единый серверный предикат сброса в демон-процессе Core (доступный из CLI и API без кликов по CEPHtmlEngine) и обязательный опрос dirty-флага/дискового слепка до формирования любого запроса пользователю.

Где НЕЛЬЗЯ обещать автоматическое recovery:

Если в момент IN_FLIGHT_MUTATION_TIMED_OUT в AE всплыло модальное окно поверх незавершённой записи, а предварительный дисковый snapshot/save-as не был сделан — автоматический kill процесса AE приведёт к потере несохранённых правок пользователя.

Если модальное окно требует семантического решения пользователя (например, выбор заменяющего шрифта или локации потерянного исходника, которого нет в рабочей папке), автоматически нажимать Escape/OK допустимо только для информационных баннеров, явно внесённых в белый список безопасного закрытия.

Вопрос 3. Safe interoperability и ограничения общего lease / undo / late callbacks

Сериализация в одном процессе AE: поскольку движок ExtendScript однопоточный, а lease в Core не блокирует Kumo на уровне ОС, при совместном использовании (вариант B или временный C) запрещено параллельное обращение к одному процессу AE. Вся работа с одним экземпляром AE должна идти через единую серверную очередь (Single-Writer Lock) с проверкой отсутствия активного in-flight запроса.

Закрытие дыры в Kumo pull-очереди: в Kumo 0.3.2 resident pull-путь не проверяет push busy-lock. Для безопасной работы необходимо либо отключить параллельный pull-канал, либо обернуть выдачу задач в pull-очереди тем же мьютексом, который удерживает Core lease.

Вопрос 7. Возражения против слабых допущений и критерии остановки разработки (Kill Criteria)

Возражение против допущения «Глобальный запрет expressions в layer-insert защищает проект»:
В реальных коммерческих шаблонах AE почти всегда есть выражения (wiggle, привязки контроллеров цвета, авто-размер плашек). Глобальный отказ layer-insert при наличии хотя бы одного включённого выражения в проекте из 1079 элементов делает инструмент неприменимым к 90%+ реальных проектов. Проверять нужно только наличие в целевой композиции выражений, зависящих от порядкового индекса слоя (thisComp.layer(index)), и при их отсутствии (либо при вставке слоёв с пересчётом или в прекомпоз) разрешать операцию.

Возражение против допущения «Нельзя полагаться на Kumo, потому что это внешний сервис»:
Kumo 0.3.2 — это локальный open-source MCP-пакет (MIT), работающий через локальный файловый IPC/сокет на той же машине, без облачных зависимостей. Противопоставлять его Core как «чужой внешний сервис» некорректно: проверенные примитивы Kumo (включая Win32-работу с диалогами и батч-исполнитель) можно либо вызывать как подчинённый локальный адаптер под мьютексом Core, либо вендорить (встроить) непосредственно в дистрибутив Core.

Критерии остановки разработки лишней обёртки (Kill / Stop Criteria):

Stop-критерий 1 (Предметный API): запретить добавление в Core новых узкоспециализированных предметных пакетов под единичные задачи (вроде отдельных контрактов под каждый вид слоёв/эффектов), если для этого можно выполнить типизированный батч примитивов (import + duplicate + moveBefore + replaceSource) внутри одного проверяемого чекпойнта Core (Pre-Digest 
→
→ Batch Execution 
→
→ Post-Digest & Frame Check).

Stop-критерий 2 (Бюджет на P0/P1): если устранение искусственных потолков Core (500 items, 24 KiB lifecycle, 64 MiB save) и развязка PENDING_READ_TIMED_OUT потребуют перепроектирования формата хранения истории Core дольше, чем занимает обёртка Kumo файловым чекпойнтом и единым мьютексом очереди — заморозить предметные пакеты Core (media-import, layer-insert, photo-placeholder) и оставить за Core исключительно роль Session & Checkpoint Supervisor (Вариант B) либо перейти на Вариант D.

Stop-критерий 3 (Накладные расходы на обёртку): если время pre-flight/post-flight проверок Core на проекте в 1000+ элементов превышает 5–10 секунд (при том, что сам монтаж занимает 1,83 с), запретить полные дампы проекта в пользу легковесного Target Comp Digest по целевому compId.

4. Итоговый вердикт и приоритетный план действий

Вердикт: Отклонить как чистый Вариант A (разработка изолированного Core-only со своим предметным API под каждый workflow), так и неконтролируемый Вариант C (два независимых MCP без общего замка). Принять Вариант B (Core как тонкий Control Plane / Checkpoint & Lease Authority + Kumo 0.3.2 как подчинённый Batch Execution Engine / вендоринг его Win32 и DOM-примитивов) с исправленным порядком фаз (сначала P0 по готовности и лимитам, затем в P1 — интеграция батча под защитой Core, и только в P2 — решение о вендоринге кода внутрь пакета).

Топ-3 приоритета до любых новых задач монтажа:

Внедрить перед отправкой команд в CEP/ExtendScript проверку модальных окон уровня ОС (Win32 scan из Kumo instance.dialogs) и перестать переводить сессию в owner_outcome_uncertain при таймауте операций чтения или отказах до отправки.

Заменить в Core поиск композиции в первых 500 элементах на app.project.itemByID(compId), заменить полный дамп проекта в lifecycle (256 items / 24 KiB) на компактный Target Comp Digest целевой композиции и снять лимит 64 МиБ на сохранение AEP.

Закрыть обход busy-lock в resident pull-очереди Kumo, включить stopOnError=true по умолчанию и передавать агенту единый Task Authorization Envelope с правом автоматического сохранения чекпойнт-копии AEP и сохранения авторизации после перезапуска AE.
