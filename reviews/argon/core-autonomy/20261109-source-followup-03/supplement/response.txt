Доказательство по коду (какие именно поля защищаются сейчас):

В project-lifecycle (core4/modules/project-lifecycle/executor.jsx:6–17, 73 и project-lifecycle-proof.js:76):
Функция inventory(project) строит JSON-строку массива кортежей [item.id, item.name, item instanceof CompItem ? item.numLayers : 0] в порядке 1..project.numItems. Это защищает неизменность id, полного name, полного пути file (fsName) и kind ('still' | 'av' | 'other') для каждого ранее существовавшего элемента проекта, а также гарантирует, что добавлен ровно один новый элемент с id === after.createdItemId и путём input.file.

Компактное представление, сохраняющее 100% этих инвариантов без потери полей:

В project-lifecycle: для проекта из ~1079 элементов строка JSON.stringify(rows) из кортежей [item.id, item.name, numLayers] занимает ~40–60 КиБ, что свободно помещается в транспортный кадр MAX_FRAME = 256 * 1024 (core4/protocol/json.js:3 и http-peer.js:70), но упирается в искусственные пороги if (count > 256) и if (result.length > 24576) в project-lifecycle/executor.jsx:9,15 и maxLength: 24576 в project-lifecycle/contract.json:189.

Решение без ослабления гарантий: сохранить в inventory(project) полный JSON-массив [item.id, item.name, numLayers] без урезания полей, подняв лимит count в project-lifecycle/executor.jsx:9 с 256 до 2048, а лимит длины строки inventory в executor.jsx:15 и contract.json:189 — с 24576 (24 КиБ) до 131072 (128 КиБ), что оставляет двукратный запас до MAX_FRAME (256 КиБ).

В media-import: сейчас capture(p) (media-import/executor.jsx:28–31) сериализует полный массив items дважды в одном ответе: один раз как массив snapshot.items, и второй раз внутри строки snapshot.revision = JSON.stringify([target, items, file.length, modifiedMs]) (с лимитом 32768 байт). На 1079 элементах с длинными путями file двойная сериализация превысит MAX_FRAME (256 КиБ).

Если требуется сохранить 100% проверку всех полей в Node (media-layer-proof.js:51) в пределах 256 KiB:

Во-первых, убрать дублирование полного массива items внутри строки snapshot.revision: поскольку snapshot.items уже передаётся в том же подписанном MAC-ответе /complete и валидируется в media-layer-proof.js:51, а before целиком хэшируется в broker.js:192 (baselineDigest: hash(before)) и manual-policy.js:65 (execution.baselineDigest !== hash(ctx.before)), либо вычислять revision в JSX по канонической строке items без хранения гигантской копии JSON-текста в поле revision сверх лимита, либо (если expectedRevision должен оставаться полной строкой JSON.stringify(...) для побайтового сравнения в validate(p, before) на стр. 37) заметить, что у элементов, не являющихся FootageItem с файлом (композиции, папки, солиды), file равен "".

Честная граница: если суммарный JSON snapshot (items + revision) для 1079 элементов превышает MAX_FRAME = 256 KiB, то без увеличения MAX_FRAME (в protocol/json.js:3, http-peer.js:70, recovery-inspection.js:27 и json-codec.jsx) передать два полных дампа по >128 КиБ в одном кадре нельзя. Тогда выбор строго бинарный: либо точечно поднять maxItems до 2048 и MAX_FRAME / maxLength revision до 512 KiB, либо в executor.jsx сверять неизменность существующих элементов внутри JSX (между before до confirm и after после importFile), а в Node передавать items только для FootageItem (или криптографический SHA-256 в ES3). Поскольку ExtendScript внутри AfterFX.exe однопоточный, сторонняя команда (например, тик agent.jsx в app.scheduleTask каждые 250 мс или -r dispatcher.jsx) может вклиниться только между отдельными вызовами evalScript (между inspect и mutate) либо во время модального диалога confirm(...) внутри mutate, когда AE крутит вложенный цикл сообщений ОС.

В существующих модулях Core (photo-placeholder/executor.jsx:88–91, layer-insert/executor.jsx:148–149, project-save/executor.jsx:51) повторный снимок capture(p) / snapshot(p, true) и validate(p, current) выполняются после выхода из confirm(...) и в одном непрерывном синхронном блоке перед started = true и мутацией AE DOM.

Если же модуль использует operatorConfirmation: 'registry-v1' (stdio-entry.js:97–106, как в comp-frame-export), то внутри mutate вообще нет модального вызова confirm() — проверка before.revision === p.expectedRevision, мутация и снятие after-снимка происходят в одном атомарном тике интерпретатора ExtendScript, внутрь которого ни app.scheduleTask, ни -r физически вклиниться не могут.

Честный ограниченный профиль выражений и зависимостей (без иллюзии regex-парсера):

В layer-insert/executor.jsx:24–55 обход inspectProperties проверяет два точных факта DOM: group.expressionEnabled === true и group.propertyValueType === PropertyValueType.LAYER_INDEX && (group.numKeys !== 0 || group.value !== 0).

Поскольку duplicate() вставляет новый слой в стек композиции compId и сдвигает index всех нижележащих слоёв на +1, статический анализ без исполнения движка выражений AE не может доказать, что произвольное текстовое выражение expressionEnabled === true (в этой или другой композиции) не обращается к слоям compId по числовому индексу layer(i) или numLayers.

Поэтому честный контракт имеет ровно два явных режима:

expressionPolicy: "forbid-active" (строгий режим по умолчанию, как в layer-insert): inspectLayer проверяет отсутствие expressionEnabled === true и ненулевых LAYER_INDEX-свойств; если они есть — детерминированный rejected (layer_duplicate_expression_scope).

expressionPolicy: "allow-with-frame-verify" (явно декларируемый операторский профиль для шаблонов с выражениями): модуль проверяет отсутствие PropertyValueType.LAYER_INDEX (эффектов с выпадающим списком выбора слоя, которые могут сбиться или требуют проверки), не парсит текст выражений регулярками, но явно записывает в snapshot и transactionReceipt поле unverifiedExpressionsPresent: true и требует в плане обязательного последующего шага comp-frame-export (контрольный рендер PNG с проверкой comp-frame-export-proof.js + png-proof.js).
