2. Какие готовые механизмы официального MCP/SDK или desktop MCP проверить прежде своего кода?

Разделение по трём архитектурным слоям:   
bundle.md

Протокол (Model Context Protocol Specification / @modelcontextprotocol/sdk):
В спецификации MCP разделены ошибки протокола/транспорта (JSON-RPC Error, McpError) и прикладные отказы выполнения инструмента (CallToolResult с флагом isError: true). Стоит переиспользовать именно этот паттерн: передавать доказанный terminal read failure внутри Core как структурированный конверт результата (isError: true, code), а не как необработанный транспортный throw на границе Broker.   
bundle.md

Transport Supervisor (управление процессами, IPC, lease):
Официальный @modelcontextprotocol/sdk предоставляет базовые StdioServerTransport и StdioClientTransport (модель 1:1), но не содержит разделяемого между несколькими клиентами single-owner демона, аутентифицированного local IPC, controller lease и журнала begin/complete с защитой от replay. Готовые desktop-прокси экосистемы MCP решают лишь конвертацию stdio <-> HTTP/SSE, поэтому замена вашего Node Core нецелесообразна из-за высокого migration cost и потери уже реализованных гарантий.   
bundle.md
Ещё 1

AE Semantics (Adobe CEP Resources <-> ExtendScript):
Взаимодействие через CSInterface.evalScript, однопоточная блокирующая природа ExtendScript и привязка к конкретному процессу AE не покрываются универсальными MCP-библиотеками и остаются полностью в зоне ответственности вашего адаптера.   
bundle.md

3. Как минимально различить completed read rejection и uncertain на owner boundary, и какие 2–4 регрессии нужны?

Механизм на границе Broker -> attachment-owner:
Вместо выбрасывания нетипизированного исключения в Broker при распознанном terminal read failure от http-peer:   
bundle.md

Возвращать из Broker типизированный результат (например, { status: 'rejected', terminal: true, mutating: false, code }) либо выбрасывать специализированный подкласс ошибки TerminalReadRejectionError с явным флагом isCertainTerminalRejection = true.

В attachment-owner внутри блока catch проверять этот флаг: если отказ терминальный и пришёл от http-peer, закрывать запись журнала со статусом completed (rejected) и возвращать код ошибки клиенту.   
bundle.md

Любое иное исключение (таймаут, обрыв сокета, ECONNRESET, неклассифицированный сбой до получения ответа от http-peer) по-прежнему переводить в owner_outcome_uncertain (UNKNOWN).   
bundle.md

Минимальный набор из 4 регрессий (без большой матрицы):

Known Terminal Read Rejection (Unit/Boundary): http-peer отдаёт известный код отказа чтения -> attachment-owner возвращает этот код клиенту, статус UNKNOWN не возникает, сессия не рвётся.   
bundle.md

Uncertain Transport Timeout/Drop (Unit/Boundary): обрыв связи или таймаут до ответа http-peer -> операция гарантированно переходит в owner_outcome_uncertain (UNKNOWN), автоматический повтор заблокирован.   
bundle.md

CEP Absent -> Connect -> Read (Live Smoke): запрос при закрытой/отключённой панели отдаёт предсказуемый отказ -> после открытия/подключения панели чтение статуса проходит штатно.   
bundle.md

Idle Disconnect / Re-attach Diagnostics (Live Smoke): имитация потери attachment между двумя вызовами -> фиксация точной причины разрыва в диагностике и успешное восстановление без перезапуска Node Core.   
bundle.md

4. Какое reconnect поведение даёт лучший UX без повторения side effects?

Автоматическое восстановление канала (Transport), но строгий запрет повтора операций (Command):

Убрать жесткий тупик по таймеру в CEP: вместо прекращения попыток после короткого окна ожидания (требующего ручного нажатия Connect) перевести CEP-панель на фоновый reconnect с экспоненциальным backoff (например, 1s -> 2s -> 5s -> 10s cap), пока панель открыта в AE. Кнопку Connect оставить как принудительный триггер немедленного сброса таймера (Retry Now).   
bundle.md
Ещё 1

Zero Command Replay: если разрыв произошёл во время выполнения команды, команда получает статус UNKNOWN и никогда не переотправляется при переподключении сокета.   
bundle.md

Read-Only Handshake при переподключении: в момент восстановления связи CEP автоматически передаёт в Core только легковесный паспорт сессии (PID процесса AE, путь к текущему проекту), автоматически снимая статус потери attachment без выполнения отложенных действий.   
bundle.md

6. Как ограничить исследование project lifecycle без обещания polling-надёжности и большого SDK-проекта?

Ограничить задачу фиксацией легковесного Pre-flight Fingerprint (Timebox: до 1–2 часов на проверку без написания фоновых вотчеров):

Не использовать C++ AEGP SDK и не запускать периодический polling через evalScript (который конкурирует за основной поток After Effects).

Проверять контекст строго в момент вызова (on-invocation pre-flight):

На стороне Node Core (асинхронно, без участия AE) при необходимости считывать fs.stat (mtime, size) файла .aep на диске.

В прологе целевого ExtendScript-вызова за одну операцию сверять app.project.file.fsName, app.project.dirty и имя/ID целевой композиции.

Для краевого сценария same-path open/revert/replacement (когда файл перезагружен в память AE через Revert или подменён по тому же пути) официально задокументировать, что автоматический транспортный детект не гарантируется, а защита обеспечивается требованием native confirm / проверкой сессионного маркера перед мутацией.
