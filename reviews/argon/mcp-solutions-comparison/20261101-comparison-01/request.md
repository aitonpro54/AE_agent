# Argon: независимое сравнение существующих MCP-решений

Review ID: 20261101-comparison-01. Stage: mcp-solutions-comparison. Type: research.
Base context: 6fcee4cdd213759e6e1f351657b19f6b919f15df.

## Задание

Это отдельное параллельное поручение пользователя: сравнить существующие MCP
решения в новом диалоге Argon. Найти готовые способы подключения, отключения,
восстановления и диагностики desktop automation, особенно Adobe After Effects.
Проверить, не покрывают ли они уже значительную часть нашей базы эффективнее.
Рассматривать честно и замену нашего компонента, и частичное переиспользование.
Не исходить из обязательности сохранения собственного Core или всех его усложнений.

## Контекст для сравнения

Локальная Windows программа: Codex -> stdio MCP client -> общий Node owner ->
CEP/ExtendScript -> After Effects. Несколько клиентов наблюдают, один управляет.
Есть typed modules, очередь/журнал команд, no replay при UNKNOWN, known-error
диагностика, штатные операции stop/update/recovery. Реальное чтение проекта есть;
полная ordinary-cycle устойчивость и native mutation acceptance ещё не закрыты.
Reconnect панели после длительного ожидания иногда требует ручного Connect.
Automatic project lifecycle отсутствует; после нового AE используется проверенная
host binding, mutation требует проверки текущей цели и native подтверждения.

Цель пользователя — сократить время, число проверок и токены на доводку базы.
Titles/Slideshow отложены. Надёжность side effects важна, но не надо объявлять
любой наш существующий guard безусловно необходимым: оцени цену/пользу и альтернативы.

## Исходные кандидаты, расширяй лишь при явной пользе

- https://github.com/kumoproductions/mcp-aftereffects
- https://github.com/23d1/after-effects-mcp
- Другие AE MCP при существенно иной архитектуре/зрелости.
- Официальные MCP specification/SDK: lifecycle, stdio, streamable HTTP,

- FastMCP и близкие transport/proxy/supervisor решения; desktop пример Blender
  или другого stateful приложения при конкретном переносимом механизме.

## Обязательные вопросы

1. Что уже реализовано в этих решениях: startup, idle reconnect, disconnect,
   client detach, приложение отсутствует/перезапущено, concurrency, timeout,
   late result, диагностика и восстановление? Ссылки на код сильнее README claims.
2. Где находится execution state и кто владеет реальным приложением? Отличай
   транспортную доставку/повтор SSE событий от повторного выполнения AE-команды.
3. Какие решения можно взять целиком, какую часть — отдельно, а что потребует
   собственного AE-specific adapter? Укажи лицензии, зависимости и Windows support.
4. Сравни три стратегии: продолжить текущую базу; заменить transport/MCP shell;
   заменить большую часть Core готовым AE MCP. Укажи migration/regression cost
   качественно, без выдуманных часов, процентов экономии или benchmarks.
5. Самая дешёвая достаточная архитектура для одного пользователя и нескольких
   чатов? От каких требований можно явно отказаться и с каким последствием?
6. Есть ли реальное решение same-path project reopen/revert detection в AE,
   или только polling пути/ID? Отдельно факт, гипотеза, неизвестное.
