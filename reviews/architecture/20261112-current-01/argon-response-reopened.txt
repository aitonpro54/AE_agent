Вопрос 3: Где Pro переоценивает или недооценивает риск (close() и условные пути generic receiver/validator)

Scope замечания close() (core4/runtime/attachment-owner.js:215–220 и core4/runtime/owner-entry.js:69–73):

Pro правильно нашёл отсутствие shared closing promise и превращение повторного close() в no-op после ошибки runtime.close().

Что Pro недооценил: в owner-entry.js:69–73 на SIGTERM и SIGINT навешивается обработчик без { once: true }, который вызывает runtime.close().then(() => { process.exitCode = 0; }, ...). Если runtime.close() проходит через attachmentOwner.close(), то при повторном сигнале во время дренирования/ошибки закрытия второй вызов немедленно попадает в if (closed) return; (attachment-owner.js:216) и сбрасывает process.exitCode в 0. Кроме того, внутри attachmentOwner.close() не выставляется frozen = true, тогда как admitted() (строка 84) проверяет if (frozen || workFacts().resetPending), но не проверяет closed.

Где предел доказательства: функция start(..., { mode: 'owner' }) в runtime/stdio-entry.js не включена в срез, поэтому мы не видим обёртку runtime.close(), которую вызывает owner-entry.js:72 и которая сама вызывается на строке attachment-owner.js:220.

Условные пути generic receiver и validator (AE-06, AE-07):

Как показано при разборе AE-06, в core4 сосуществуют два разных контура приёма:

Контур 1 (Fixture / Legacy M1): core/receiver.js + integrations/cep/host-dispatcher.js. Здесь exact(value, keys) из protocol/json.js проверяет, что ключи объекта входят в разрешённый список keys (allowlist). Для inspect список ['target', 'revision', 'sourceId', 'text', 'protected'] (receiver.js:34) случайно пропускает 4-польный snapshot titles-current-target (так как {target, text, protected, revision} — подмножество этих 5 ключей), но отвергнет project-inspection. Для mutate список ['outcome', 'snapshot', 'code'] отвергает transactionReceipt из titles-current-target/executor.jsx:102 и переводит команду в unknown (receiver.js:41–42).

Контур 2 (Production CEP / HTTP Peer): integrations/cep/http-peer.js + cep/js/poll-dispatcher.js + cep/jsx/registry.jsx. Здесь AECore4Host.dispatch (stdio-entry.js:286) и poll-dispatcher.js:53–55 прозрачно сериализуют и пересылают любой валидный JSON-результат mutate в http-peer.js, который валидирует его по resultProfile из композиции (operator-workflows*.json).

Следовательно, риск в AE-06 относится не к поломке titles-current-target в production, а к расхождению между старым core/receiver.js и новой системой resultProfile.

Вопрос 4: Фактическая минимальность Core, независимость модулей и одно ограниченное упрощение

G-01 — P2 — Отказ внутри bootstrapRegistry в CEP-панели теряет диагностический код registry_refresh_failed и навсегда оставляет localStorage latch без result

Источник: core4/cep/js/poll-dispatcher.js:88–118; core4/integrations/cep/http-peer.js:162–163,333–339.

Уверенность: высокая (полностью доказано показанным кодом).

Сценарий:

При /link с registryRequired === true http-peer.js:336 открывает команду verify-registry (phase: 'inspect') в completionStore и возвращает панели bootstrap challenge.

Панель вызывает bootstrapRegistry(options) (poll-dispatcher.js:88), который до вызова evalScript записывает в localStorage ключ aeagentcore4-registry-<installationId> без поля result (строки 92–95) и взводит nativeGuard.active = token.

Если внутри ExtendScript (строка 99) возникает ошибка (например, не совпал registryBuildId или ошибка чтения registry.jsx), блок catch(e) в ExtendScript штатно возвращает JSON {"version":1,"nonce":"...","code":"registry_refresh_failed"}.

Однако в JS-колбэке на строках 105–106 код безусловно вызывает exact(result, ['version', 'nonce', 'registryBuildId', 'refreshed']). На объекте с полем code вызов exact() выбрасывает исключение до строки 107 (record.result = result; save();) и до вызова options.complete(...).

Последствия:

Конкретный код ошибки registry_refresh_failed теряется.

Хотя ExtendScript уже завершился и это чисто проверочная (inspect) операция без мутации проекта, options.complete не вызывается (http-peer.js ждёт истечения registryTimeoutMs и переводит bootstrap в unknown на строке 163), а в localStorage панели остаётся незакрытый record без result. Любой следующий вызов bootstrapRegistry в этой установке немедленно падает на строке 90 (options.storage.getItem(key) !== null → registry_bootstrap_unknown_no_replay).

Дополнительно: если options.csInterface.evalScript выбросит синхронное исключение (poll-dispatcher.js:56 и :115), nativeGuard.active (и active = true на строке 43) вообще не сбрасываются в catch (e) { reject(e); }.

Предел вывода: поведение reloadIdle после строки 66 (poll-dispatcher.js:67–87) не включено в срез, но строка 90 в bootstrapRegistry проверяет options.storage.getItem(key) !== null безусловно.
