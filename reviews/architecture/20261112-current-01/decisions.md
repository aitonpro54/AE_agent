# Архитектурное решение по Core 4.2.6 — 12 ноября 2026

## Итог

Каркас сохранить. Реализация уже содержит содержательную границу между
workflow-продуктом, ограниченной операцией AE и общим допуском Core. Цель
минимального ядра выполнена частично: готовые возможности выбираются
декларативно, но новые proof/result profiles и некоторые специальные случаи
ещё требуют общей интеграции. Основная стоимость сопровождения сосредоточена
в startup, связывании локальной среды и нескольких восстановительных состояниях.

Точный source snapshot: `6d40cc228d9f2e18c672af5782033be305b82917`.
Позднейшие коммиты этого аудита меняют только его документы и evidence.
Current native proof ограничен чистой установкой и одним свежим чтением
пустого AE; его нельзя расширять до всех мутаций и всего release.

## Принятые выводы

1. Сохранить installation owner, thin clients, controller lease, server-owned
   evidence/build/proposal, admitted typed executors, checkpoints, read-back
   и UNKNOWN/no-replay. Внешние продукты продолжают владеть заданиями,
   шаблонами и compiler; authority остаётся у Core.
2. **AE-04, P2:** нижний close не сохраняет общий незавершённый promise.
   Штатный Owner сериализует закрытие сверху; это ограничивает влияние.
   Исправление не должно снимать ранний запрет admission или терять ошибку cleanup.
3. **AE-05, P2:** thin client и упаковщик зависят от runtime entry ради
   composition/registry helpers; общий bootstrap знает предметные proof profiles.
   Выделение чистой спецификации состава — наиболее ограниченный кандидат
   на уменьшение зависимости без миграции истории и authority.
4. **G-01:** ошибка registry bootstrap теряет точный диагностический код и
   оставляет неопределённый latch. Signed retirement уже существует;
   сохранение guard после неопределённого eval нельзя автоматически отменять.
5. **G-02:** catalogRevision не отражает всю выбранную композицию, когда
   вычисляется по последнему добавленному manifest. Это неполнота ревизии,
   а не доказанная недетерминированность одинаковой сборки. Package hash и
   artifact pins сохраняют отдельные гарантии целостности.
6. **AE-01–03:** существенные границы применимого текущего proof. Recovery
   механизмы и прежние проверки существуют. Отсутствие их в bundle не
   доказывает отсутствия в проекте. Применимость старых результатов проверяется
   по затронутой closure; совпавший controller-lease PASS переиспользуем,
   другие проверенные несовпавшие keys не объявляем регрессией.

AE-07, AE-08 и G-03–05 сохраняются как ограниченные contract/metadata/liveness
вопросы с отдельным статусом, без заявления найденной ошибки действующего
пользовательского workflow. Подробный разбор каждого пункта, приоритетов,
новизны и source evidence — в local-pro-triage.md и local-argon-triage.md.

## Отклонённые или суженные утверждения

- Текущая поломка Titles из различия generic receiver/result shape не следует:
  active HTTP validator принимает transactionReceipt.
- Утверждение Argon «receiver.js не упакован» неверно: он входит через
  core/artifact closure. Наличие файла и активный маршрут — разные вопросы.
- Расширение повторного нижнего close на обычный Owner shutdown не подтверждено:
  сверху действуют shared closing promise, maintenance и admission fence.
- «Вечная» registry-блокировка после возвращённого callback чрезмерна:
  существует проверяемый retirement. Автоматическая очистка latch из этого
  не следует.
- Полнота security, crash recovery, automatic relaunch и mutation acceptance
  не доказана выбранным пакетом. Это не равнозначно найденному обходу защиты.

## Следующие безопасные блоки

Это рекомендации для будущих поручений, без автоматического начала реализации
и без новых startup/release gates для пользовательских рабочих задач.

1. Адресно закрыть диагностику bootstrap и семантику concurrent/rejected close.
   Приёмка: общий promise cleanup, явный diagnostic result, прежние fences,
   UNKNOWN/no-replay и signed retirement сохраняются.
2. Выделить pure composition/registry metadata и привести catalogRevision к
   полному выбранному составу. Приёмка: эквивалентные package/registry pins,
   минимальный client initialize/version/tools-list, адресные dependency checks.
3. Свести применимое evidence для одного полного supported workflow и
   перепроверить только оставшийся затронутый переход. Native-приёмка нового
   сценария или identity назначается отдельным scope; settled IDs не повторять.

Порядок уточнён после локальной сверки: сначала небольшие подтверждённые
ошибки контрактов/диагностики, затем структурное уменьшение зависимости.
Это локальное решение о рекомендации, не запуск работ по внешнему verdict.
